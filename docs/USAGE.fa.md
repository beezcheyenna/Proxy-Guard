# نصب و استفاده

[English](USAGE.en.md) · [简体中文](USAGE.md) · [日本語](USAGE.ja.md) · [Русский](USAGE.ru.md) · [فارسی](USAGE.fa.md)

Proxy Guard را روی روتری با LuCI و firewall4/nftables نصب کنید. قالب بسته را مطابق مدیر بستهٔ میان‌افزار انتخاب کنید.

## دریافت و بررسی

بسته و فایل مجموع بررسی را از یک انتشار دریافت کنید. برای opkg از IPK و برای apk از APK استفاده کنید. وابستگی‌ها را از مخزن سازگار با میان‌افزار بگیرید.

[GitHub Releases](https://github.com/beezcheyenna/Proxy-Guard/releases)

نام فایل دانلودشده را وارد کنید. خط نخست IPK را انتخاب می‌کند. برای APK از نام فایل در توضیح خط بعد استفاده کنید.

```sh
PG_PACKAGE=luci-app-proxy-guard_1.0.0-8_all.ipk
# PG_PACKAGE=luci-app-proxy-guard-1.0.0-r8.apk
awk -v f="$PG_PACKAGE" '$2 == f { print; n++ } END { if (n != 1) exit 1 }' SHA256SUMS > SHA256SUMS.selected &&
sha256sum -c SHA256SUMS.selected
```

بررسی باید برای بستهٔ انتخاب‌شده OK نشان دهد. در macOS می‌توانید `shasum -a 256 "$PG_PACKAGE"` را اجرا کنید و مقدار کامل را با سطر مربوط در `SHA256SUMS` مقایسه کنید.

SHA256 یکپارچگی فایل را با فهرست می‌سنجد. هویت منتشرکننده را جداگانه بررسی کنید و فایل و فهرست را از یک انتشار معتبر بگیرید. برای نصب آفلاین روی میان‌افزار apk، نخست وابستگی‌های هم‌نسخه را نصب کنید.

<a id="installation"></a>

## نصب و حذف

دستورهای متناسب با میان‌افزار خود را به کار ببرید. مثال نصب APK از `--no-network` برای نصب آفلاین استفاده می‌کند. وابستگی‌ها باید از قبل نصب شده باشند یا در مخزن محلی در دسترس باشند. برای نصب آنلاین وابستگی‌های موجود در مخزن‌های پیکربندی‌شده و سازگار با میان‌افزار، `--no-network` را حذف کنید. هنگام آزمایش محافظت، مسیر مدیریتی جداگانه در دسترس داشته باشید.

```sh
opkg install /tmp/luci-app-proxy-guard_1.0.0-8_all.ipk
apk --no-network --allow-untrusted add /tmp/luci-app-proxy-guard-1.0.0-r8.apk
```

```sh
opkg remove luci-app-proxy-guard
apk --no-network del luci-app-proxy-guard
```

## مهاجرت از ۰٫۳ به ۱٫۰

نسخهٔ ۱٫۰ را با پیکربندی تازه راه‌اندازی کنید. نصب مستقیم ۱٫۰ روی بسته‌های منتشرشدهٔ ۰٫۳ و بازگشت از ۱٫۰ به ۰٫۳ به‌عنوان مسیرهای مهاجرت پشتیبانی‌شده تأیید نشده‌اند. هر دو بسته `/etc/config/proxy_guard` را به‌عنوان فایل پیکربندی معرفی می‌کنند. مدیر بسته ممکن است فایل تغییریافتهٔ ۰٫۳ را نگه دارد. نصاب بعضی پیش‌فرض‌های قدیمی بررسی را به‌روز می‌کند و برخی گزینه‌های غایب را می‌افزاید. پیش از استفاده از تنظیمات باقی‌مانده در ۱٫۰، آن‌ها را بررسی کنید.

دسترسی مدیریتی مستقلی در نظر بگیرید. از تنظیمات ۰٫۳ پشتیبان بگیرید و اطلاعات ورود و بسته‌های همان نسخه را برای بازیابی در جای امن نگه دارید. محافظت نسخهٔ قبلی را صریحاً غیرفعال کنید. اگر Pro نصب است، ابتدا سیاست سرور را طبق بند بعدی بررسی کنید و سپس Pro را حذف کنید. بعد از حذف نسخهٔ عادی ۰٫۳، نسخهٔ ۱٫۰ را نصب کنید. اگر تنظیمات قدیمی باقی مانده‌اند، در «پیکربندی و عیب‌یابی» گزینهٔ «بازگردانی پیش‌فرض‌ها و پیکربندی دوباره» را انتخاب کنید. فقط محدودهٔ محافظت، استثناها، تنظیمات SOCKS و زمان‌بندی‌هایی را که بازبینی کرده‌اید وارد کنید.

پیکربندی تازهٔ ۱٫۰ از HTTPS رسمی استفاده می‌کند و تطبیق IPv4 خروجی خاموش است. اگر در تنظیمات قدیمی روش بررسی اتصال مشخص نشده باشد، ۱٫۰ از HTTPS رسمی استفاده می‌کند. اگر می‌خواهید همچنان gstatic و Ubuntu را بررسی کنید، HTTPS سرویس‌های دیگر را در تنظیمات بررسی اتصال انتخاب کنید.

اگر ۰٫۳ Pro سرور VPS را مدیریت می‌کند، تا وقتی مسیر مدیریت در دسترس است سیاست‌هایی را که باید حذف شوند از طریق ۰٫۳ Pro لغو کنید و نتیجه را روی VPS بررسی کنید. نسخهٔ ۱٫۰ با ۰٫۳ Pro یکپارچه نیست. قواعد موجود VPS، عامل و منابع Cloudflare را جداگانه مدیریت کنید. [راهنمای بازیابی بایگانی‌شده](https://github.com/beezcheyenna/Proxy-Guard/blob/987ff38a25c1a00f2c05753f7503e134391a4a3a/docs/RECOVERY.fa.md)

## پیکربندی نخست

**پس از توقف سرویس Proxy Guard ممکن است قواعد دیوار آتش همچنان دسترسی را مسدود کنند.** برای رفع مسدودی، محافظت را صریحاً غیرفعال کنید یا [مراحل بازیابی](RECOVERY.fa.md) را انجام دهید.

**موفقیت «آزمایش پراکسی فعلی» فقط دسترسی همان درخواست آزمایشی را تأیید می‌کند.** زمان‌بندی، درخواست API یا ناموفق بودن یک بررسی مستقل همچنان می‌تواند باعث مسدودی باشد.

در «سرویس‌ها → Proxy Guard» راهنما را باز کنید و رابط‌های ورودی، محدودهٔ IPv4 و IPv6، استثناهای محلی و درگاه SOCKS را بررسی کنید. نخست حالت فقط پایش را انتخاب کنید. ذخیره و اعمال، خودآزمایی و مهلت ۳۰ ثانیه‌ای تأیید را آغاز می‌کند. در صورت خطا یا تأیید نشدن، تنظیمات بازگردانده می‌شوند.

بررسی رسمی HTTPS به‌صورت پیش‌فرض از طریق SOCKS محلی به نشانی ثابتی متصل می‌شود. بررسی شخص ثالث زمان‌بندی و آستانهٔ جداگانه دارد. تطبیق IPv4 خروجی در ابتدا خاموش است و پس از فعال شدن از نشانی پاسخ رسمی استفاده می‌کند. سرویس پشتیبان شخص ثالث فقط پس از پایان مهلت سرویس اصلی درخواست می‌شود.

بررسی رسمی HTTPS به‌طور پیش‌فرض پس از پایان هر بررسی ۳ ثانیه منتظر می‌ماند و مهلت هر درخواست ۲ ثانیه است. بررسی شخص ثالث بعد از هر دور ۱۰ ثانیه صبر می‌کند و مهلت هر مقصد ۴ ثانیه است. مقصدهای پیش‌فرض gstatic و Ubuntu هستند و در هر دور عادی موفقیت یک مقصد کافی است. در حالت محافظت و پایش عادی، دو بررسی رسمی ناموفق یا سه دور شخص ثالث ناموفقِ پیاپی خرابی را تأیید می‌کند. پیش‌فرض بازیابی در هر دو حالت دو بررسی یا دو دور موفق پیاپی است. در دورهٔ پایش حساس، یک بررسی ناموفق هم می‌تواند باعث مسدودسازی شود.

اگر مهلت هر دو درخواست متنی IPv4 تمام شود ولی بررسی اتصال موفق باشد و عدم تطابقِ رفع‌نشده‌ای وجود نداشته باشد، نتیجهٔ همین بررسی به‌تنهایی باعث مسدودسازی نمی‌شود. اگر مهلت نشانی اصلی پیش‌فرض `https://api.ipify.org/` تمام شود، از `https://4.ident.me/` استفاده می‌شود. اگر نشانی اصلی سفارشی هیچ پشتیبانی نداشته باشد، پایان مهلت به معنی در دسترس نبودن تطبیق است و مطابق حالت و آستانهٔ تنظیم‌شده پردازش می‌شود. پس از تأیید عدم تطابق، بازیابی به دریافت IPv4 منطبق نیاز دارد.

تا زمانی که قواعد نیاز به بررسی دارند، دکمهٔ نگه‌داشتن تنظیمات غیرفعال است و شمارش معکوس اولیه ادامه دارد. با پایان مهلت، روتر تنظیمات قبلی را حتی اگر صفحه بسته شده باشد بازمی‌گرداند.

<a id="test-current-proxy"></a>

## آزمایش پراکسی فعلی

«آزمایش پراکسی فعلی» با تنظیمات ذخیره‌نشدهٔ فرم از طریق SOCKS انجام می‌شود و نتیجه، زمان پاسخ و IPv4 خروجی موجود را نشان می‌دهد. «اجرای عیب‌یابی کامل» در همان پنجره از تنظیمات اعمال‌شدهٔ پراکسی استفاده می‌کند. تغییر محافظت با «ذخیره و اعمال» انجام می‌شود.

صفحهٔ وضعیت تعداد بررسی‌های ناموفق پیاپی و دلایل فعال مسدودسازی را نشان می‌دهد. خطای زیر آستانه ممکن است دسترسی را قطع نکند. زمان‌بندی، درخواست API و خطای اتصال می‌توانند هم‌زمان فعال باشند.

API محلی در نصب تازه غیرفعال است. پس از فعال‌سازی می‌توانید با UUID نمایش‌داده‌شده در LuCI وضعیت را بخوانید، عیب‌یابی کنید و مسدودی مدت‌دار را آغاز یا لغو کنید.

## آزمون محافظت هنگام راه‌اندازی

یک مسیر مدیریت مستقل در دسترس نگه دارید و روترِ اجراکنندهٔ Proxy Guard را راه‌اندازی مجدد کنید. از دستگاه تحت محافظت بررسی کنید که هنگام راه‌اندازی روتر، ترافیک اینترنت مسدود بماند و فقط پس از موفقیت بررسی‌های بازیابی دوباره برقرار شود.

<a id="local-api"></a>

## رابط محلی API

در LuCI، «API کنترل شبکه محلی» را فعال کنید، «ذخیره و اعمال» را بزنید و اگر درخواست شد تنظیمات را تأیید کنید. **UUID رابط API** را از همان زبانه کپی کنید و در هر درخواست `Authorization: Bearer YOUR_UUID` را بفرستید.

**UUID اعتبارنامهٔ دسترسی است.** خاموش و روشن کردن دوبارهٔ API، یا راه‌اندازی مجدد روتر در حالی که API فعال است، UUID تازه‌ای ایجاد می‌کند. اعتبارنامهٔ برنامه‌های فراخوان را به‌روز کنید. برای فراخوانی، UUID رابط کافی است. UUID در پاسخ درخواست پذیرفته‌شده و در گزارش رویدادهای LuCI برای مدیران دیده می‌شود. پیش از اشتراک‌گذاری پاسخ یا گزارش، آن را بپوشانید.

**از نشانی HTTPS مدیریت روتر استفاده کنید.** API درخواست‌های محلی روتر و مبدأهایی را می‌پذیرد که مسیر برگشت مستقیم از دستگاهی در ناحیهٔ دیوار آتش با نام `lan` دارند. اگر مسیر به دروازهٔ دیگری نیاز داشته باشد، درخواست رد می‌شود. ناحیه‌های دیگر، VLAN مسیریابی‌شده یا VPN ممکن است پاسخ `403 lan_required` بگیرند. از نام میزبان منطبق با گواهی استفاده کنید. برای CA خصوصی یا گواهی خودامضا، گواهی مورد اعتماد را با گزینهٔ `--cacert` در curl مشخص کنید.

`router.example` را با نام میزبان HTTPS مدیریت روتر و `YOUR_UUID` را با UUID فعلی جایگزین کنید. JSONهای زیر مقادیر نمونه دارند. درخواست‌های POST دسترسی اینترنت را در محدودهٔ محافظت تغییر می‌دهند. فقط در صورت نیاز آن‌ها را اجرا کنید.

| روش | مسیر | کاربرد |
| --- | --- | --- |
| GET | [`/status`](#api-status) | خواندن وضعیت محافظت |
| GET | [`/diagnostics`](#api-diagnostics) | اجرای یک‌بارهٔ عیب‌یابی |
| POST | [`/block`](#api-block) | درخواست مسدودی موقت اینترنت |
| POST | [`/cancel`](#api-cancel) | لغو مسدودی موقت |

<a id="api-status"></a>

### خواندن وضعیت محافظت

`GET /status` وضعیت فعلی دیوار آتش و درخواست‌های فعال مسدودسازی را می‌خواند. نمونه یک مسدودی موقت فعال دارد. برای برنامه‌ها از `enforcement` و `block_reasons` استفاده کنید. `reason` متن نمایشی است. `last_check` زمان آخرین بررسی کامل‌شده بر حسب ثانیهٔ یونیکس است و اگر بررسی ثبت نشده باشد ممکن است وجود نداشته باشد. وقتی وضعیت نامعلوم است یا قواعد وجود ندارند یا هنوز تأیید نشده‌اند، `blocked` نیز ممکن است وجود نداشته باشد. برای تشخیص این وضعیت‌ها `enforcement` را بخوانید.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' 'https://router.example/cgi-bin/proxy-guard-api/status'
```

<a id="api-diagnostics"></a>

### اجرای عیب‌یابی

`GET /diagnostics` از SOCKS محلی یک بررسی اجرا می‌کند و نتیجه را در همان پاسخ برمی‌گرداند. در «نشانی تازه‌سازی API» مقصد پیش‌فرض مسیر `/` در PGHB است. برای دریافت سرآیندهای کامل مثال، ابتدا `/f` را انتخاب و تنظیم را اعمال کنید. [راهنمای پاسخ PGHB](PGHB.fa.md)

```sh
curl -H 'Authorization: Bearer YOUR_UUID' 'https://router.example/cgi-bin/proxy-guard-api/diagnostics'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "diagnostics": {
    "ok": true,
    "source": "https://hb.pghb.app/f",
    "checked_at": 1794628800,
    "http_code": 200,
    "curl_code": 0,
    "milliseconds": 117,
    "nonce_verified": true,
    "headers": [
      {
        "name": "x-pghb-ip",
        "value": "203.0.113.10"
      },
      {
        "name": "x-pghb-tls",
        "value": "TLSv1.3"
      },
      {
        "name": "x-pghb-nonce",
        "value": "0123456789abcdef0123456789abcdef"
      }
    ]
  }
}
```

`diagnostics.headers` نام و مقدار رشته‌ای سرآیندهای `X-PGHB-*` را به ترتیب پاسخ برمی‌گرداند. تکرار `X-PGHB-IP` یا `X-PGHB-Nonce` باعث رد اعتبارسنجی می‌شود. سایر سرآیندهای تکراری می‌توانند در رکوردهای جدا بازگردند. برای مقدارهایی خارج از UTF-8، `"encoding":"base64"` افزوده می‌شود. `checked_at` زمان یونیکس بر حسب ثانیه است.

<a id="api-block"></a>

### درخواست مسدودی موقت

`POST /block` به حالت محافظت فعال نیاز دارد و بر محدودهٔ تنظیم‌شده اثر می‌گذارد. زمان پیش‌فرض ۳۰۰ ثانیه و سقف اولیه ۳۶۰۰ ثانیه است. حذف `seconds` یا مقدار `0` از پیش‌فرض تنظیم‌شده استفاده می‌کند. اگر `request_id` را نفرستید، روتر آن را می‌سازد. شناسهٔ دلخواه باید ۸ تا ۶۴ نویسه از حروف لاتین، رقم، خط تیره یا زیرخط باشد. تکرار شناسهٔ فعال با همان مدت، زمان انقضا را تغییر نمی‌دهد. مدت متفاوت خطای `409 request_conflict` می‌دهد.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' \
  -H 'Content-Type: application/json' \
  --data '{"seconds":120,"request_id":"example-block-01"}' \
  'https://router.example/cgi-bin/proxy-guard-api/block'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "request_id": "example-block-01",
  "effective": true,
  "remaining": 120,
  "seconds": 120
}
```

### لغو مسدودی موقت

`POST /cancel` به شناسهٔ درخواست نیاز دارد. مالکیت از UUID احراز هویت‌شده و شناسهٔ درخواست تعیین می‌شود. دستگاه‌ها و برنامه‌هایی که از یک UUID استفاده می‌کنند هویت مشترک دارند. برای یک شناسه با قالب معتبر، حتی اگر درخواست متناظر منقضی شده یا پیدا نشود، API می‌تواند `cancelled: true` برگرداند. `effective` و `remaining` وضعیت مسدودی باقی‌ماندهٔ API را نشان می‌دهند. زمان‌بندی و ناموفق بودن بررسی اتصال ممکن است همچنان ترافیک را مسدود کنند.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' \
  -H 'Content-Type: application/json' \
  --data '{"request_id":"example-block-01"}' \
  'https://router.example/cgi-bin/proxy-guard-api/cancel'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "request_id": "example-block-01",
  "cancelled": true,
  "effective": false,
  "remaining": 0
}
```

### خطاهای رایج

| وضعیت HTTP و خطا | موارد بررسی |
| --- | --- |
| `401 authentication_required` | UUID فرستاده نشده یا معتبر نیست. مقدار فعلی را در LuCI بررسی کنید. |
| `403 https_required`، `api_disabled` یا `lan_required` | HTTPS، وضعیت فعال بودن API و مسیر به ناحیهٔ `lan` را بررسی کنید. |
| 409 `configuration_pending`، `configuration_changed`، `protection_not_active` یا `request_conflict` | پیش از تکرار عیب‌یابی، تنظیمات را تأیید کنید یا حالت محافظت و مدت مربوط به شناسهٔ فعال را بررسی کنید. |
| 429 | زمان انتظار عیب‌یابی یا سقف درخواست‌های فعال اعمال شده است. اگر `Retry-After` وجود دارد، به همان مدت صبر کنید. |
| 502 / 504 | عیب‌یابی ناموفق بود یا مهلت آن تمام شد. در صورت وجود، جزئیات را در `diagnostics` ببینید. |
| 503 `busy` | عملیات دیگری در جریان است. پیش از تلاش دوباره، به تعداد ثانیه‌های `Retry-After` صبر کنید. |
| 503 `policy_not_ready`، `request_state_unavailable` یا `firewall_failed` | سیاست دیوار آتش آماده نیست، وضعیت درخواست در دسترس نیست یا به‌روزرسانی قواعد ناموفق بوده است. پیش از تلاش دوباره با همان شناسهٔ درخواست، وضعیت محافظت و گزارش رویدادها را بررسی کنید. |
