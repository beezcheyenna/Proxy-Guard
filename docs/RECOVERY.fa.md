# بازیابی در شرایط خطا

برای استاندارد `0.3.0-21` و Pro `0.3.1-5`. محافظت روتر و سیاست راه‌دور VPS جداگانه مدیریت می‌شوند.

خاموش‌کردن محافظت و انقضای تأیید در ماشین مجازی ایزولهٔ OpenWrt 24.10.8 بررسی شد. حذف روی VPS در ماشین مجازی Ubuntu و Alpine و در آزمون قبلی چرخهٔ عمر چهار توزیع بررسی شد. برای حالت بازیابی اختصاصی فریم‌ور یا خرابی سامانهٔ فایل، از روش مربوط استفاده کنید. [ماتریس آزمون](TEST-MATRIX.fa.md) را ببینید.

## ۱. دسترسی مدیریت را نگه دارید

- نشست SSH، کنسول سریال، کنسول ماشین مجازی یا کنسول ارائه‌دهندهٔ VPS را نگه دارید. اگر مدیریت شبکه قطع است، از کنسول مستقل و روش بازیابی همان فریم‌ور استفاده کنید.
- خاموش‌کردن محافظت ممکن است دسترسی مستقیم کلاینت را برقرار کند. در صورت نیاز، ابتدا مسیر بیرونی کلاینت را قطع کنید.
- قانون‌های سیستم، فایل قفل و تراکنش در انتظار را نگه دارید. پاک‌سازی کلی فایروال یا حذف تراکنش می‌تواند مدیریت و بازیابی را مختل کند.

## ۲. LuCI در دسترس نیست ولی SSH یا کنسول روتر کار می‌کند

بررسی‌های فقط‌خواندنی را با root اجرا کنید:

```sh
/usr/libexec/proxy-guard status
ubus list proxy_guard
nft list tables
logread -e proxy-guard
```

نبود شیء ubus، خطای صفحهٔ LuCI و قطع پروکسی را جدا بررسی کنید. خطا را نگه دارید و ACL موجود را حفظ کنید. پس از `/etc/init.d/proxy-guard stop` ممکن است مسدودسازی nftables باقی بماند. گزارش را پیش از راه‌اندازی دوباره خصوصی ذخیره و پیش از انتشار پاک‌سازی کنید. گزارش RAM معمولاً پس از راه‌اندازی دوباره از دست می‌رود.

### خاموش‌کردن صریح محافظت استاندارد

پیکربندی UCI باید خواندنی باشد، مسیر مدیریت مستقل برقرار باشد و احتمال اتصال مستقیم کلاینت پذیرفته شده باشد. ابتدا پشتیبان بگیرید:

```sh
umask 077
cp /etc/config/proxy_guard /root/proxy_guard.before-recovery
```

پس از بررسی پشتیبان اجرا کنید:

```sh
uci set proxy_guard.main.enabled='0' &&
uci commit proxy_guard &&
printf '%s\n' '{}' | ucode /usr/lib/proxy-guard/setup-lock.uc apply &&
/etc/init.d/proxy-guard restart
```

خاموش‌کردن صریح به‌عنوان تنظیم تأییدشده ثبت می‌شود، فعال‌سازی در انتظار را کنار می‌زند و سپس سرویس دوباره راه‌اندازی می‌شود. ناظر نمی‌تواند پیش‌نویس قدیمی را دوباره اعمال کند. ویرایش UCI یا reload سرویس متوقف به‌تنهایی تراکنش را کامل نمی‌کند.

بررسی کنید:

```sh
uci -q get proxy_guard.main.enabled
/usr/libexec/proxy-guard status
nft list tables
```

انتظار می‌رود `0`، `disabled` و وضعیت اجرا `off` دیده شوند. جدول استاندارد `inet proxy_guard` حذف و `fw4` و قانون‌های دیگر حفظ می‌شوند. دسترسی واقعی تابع مسیر، فایروال و پروکسی موجود است.

اگر پیکربندی خواندنی نیست، `/etc/config/proxy_guard` را از پشتیبان مطمئن خود برای نسخهٔ متناظر بازگردانید و خاموش‌کردن صریح را اجرا کنید. اگر برنامه یا وابستگی آسیب دیده، کنسول را نگه دارید و بستهٔ مربوط را بازیابی کنید.

## ۳. پایان مهلت تأیید

پس از موفقیت خودآزمایی، روتر **۳۰ ثانیه مهلت تأیید** می‌دهد. ناظر مستقل حتی اگر مرورگر بسته یا اتصال قطع شود، تغییر تأییدنشده را بازمی‌گرداند. پس از اتصال، وضعیت و تنظیم قبلی را با قانون‌های فعال تطبیق دهید و بعد پیش‌نویس را اصلاح کنید. `pending.json` را نگه دارید. اگر ناظر، ذخیره‌سازی یا محیط اجرا خراب است، با کنسول صریح خاموش کنید و قانون‌ها را بسنجید.

## ۴. فرایند متوقف شده و مسدودسازی باقی است

هسته پس از خروج فرایند همچنان قانون‌ها را اجرا می‌کند و مجوزها ممکن است منقضی شوند. با حفظ محافظت، گزارش، ذخیره‌سازی، وابستگی، UCI و رابط‌ها را بررسی و افزونه را ترمیم و راه‌اندازی کنید. برای رفع موقت از بخش ۲ استفاده کنید. چند فرایند دستی هم‌زمان اجرا نکنید و فایل قفل را نگه دارید. پیش از فعال‌سازی دوباره و تأیید، یک کلاینت را بیازمایید.

## ۵. Pro در دسترس نیست و قانون VPS باقی مانده است

توقف همگام‌سازی تمدید را قطع می‌کند. مجوز پویای IP خانگی منقضی می‌شود ولی فهرست ثابت و سیاست پورت منتخب ممکن است باقی بمانند. نجات SSH نیازمند فعال‌سازی و تأیید قبلی و قطع هر دو ضربان احراز هویت‌شده طبق تنظیمات است. فایروال، احراز هویت SSH و گروه امنیتی ارائه‌دهنده برقرارند. نتیجهٔ نامشخص را از وضعیت راه‌دور بررسی کنید و شمارهٔ بازبینی و شناسهٔ عملیات را حفظ کنید. مدیریت روی پورت مشترک پروکسی هم ممکن است محدود شود، پس کنسول مستقل نگه دارید.

اگر کنترل برقرار است، از فرایند حذف و تأیید Pro استفاده کنید و سپس وضعیت VPS را پیش از توقف همگام‌سازی بسنجید.

### حذف قانون مؤلفه از کنسول VPS

همگام‌سازی خودکار روتر را در طول بازیابی خاموش نگه دارید. کنسول VPS و فایروال سیستم را حفظ کنید. از `/etc/proxy-guard-access/agent.json` واقعی، کلید، گواهی و وضعیت پایدار خصوصی پشتیبان بگیرید. به `companion/vps` منبع مطمئن متناظر با نسخهٔ نصب‌شده بروید و دستور سیستم خود را اجرا کنید.

Ubuntu، Debian یا Rocky Linux:

```sh
sudo sh ./uninstall.sh --remove
sudo systemctl status proxy-guard-access proxy-guard-access-policy --no-pager
sudo nft list tables
```

Alpine Linux با root:

```sh
sh ./uninstall.sh --remove
rc-service proxy-guard-access status
rc-service proxy-guard-access-policy status
nft list tables
```

استعلام وضعیت بعد از حذف ممکن است «سرویس یافت نشد» یا کد غیرصفر بدهد. اگر خود حذف خطا داد، خروجی را ذخیره و متوقف شوید. حذف‌کننده فقط سرویس، وابستگی آغاز و قانون‌های متعلق به مؤلفه را پاک می‌کند. پیکربندی، کلید و برنامه و نیز NAT، FORWARD و قانون‌های دیگر حفظ می‌شوند. پورت‌های مدیریت و سرویس را بسنجید. `pg_vps_access` نام پیش‌فرض است و نام واقعی را باید از پیکربندی خواند. اگر مالکیت جدول با پیکربندی آسیب‌دیده معلوم نیست، نخست آن را بازیابی کنید.

نصب دوباره ممکن است سیاست ذخیره‌شده را برگرداند. پیش از آن تنظیم و وضعیت را مرور کنید و بعد کنترل، مجوز پویا، حالت پورت و SSH را بسنجید. وضعیت همان نمونه و افزایش شمارهٔ بازبینی را حفظ کنید.

## ۶. بررسی پس از بازیابی

از یک کلاینت تحت محافظت، LAN، DNS، مدیریت، IPv4/IPv6، اتصال جدید و موجود، خرابی و بازیابی را بسنجید. برای آزمون محافظت هنگام راه‌اندازی، مدیریت مستقل را حفظ کنید و **روتر دارای Proxy Guard** را دوباره راه‌اندازی کنید.
