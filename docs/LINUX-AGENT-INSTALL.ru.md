# Установка Linux VPS Agent для Pro

[English](LINUX-AGENT-INSTALL.en.md) · [简体中文](LINUX-AGENT-INSTALL.md) · [日本語](LINUX-AGENT-INSTALL.ja.md) · [Русский](LINUX-AGENT-INSTALL.ru.md) · [فارسی](LINUX-AGENT-INSTALL.fa.md)

Для удалённых возможностей нужны Standard и Pro на OpenWrt и Agent на VPS. Выберите прямой HTTPS или Cloudflare Worker с Tunnel/VPC. IPK/APK устанавливается на роутере, на VPS работает Python-установщик. Нужны Python 3.10+, nftables, соответствующие возможности ядра и systemd либо OpenRC. См. [совместимость](COMPATIBILITY.ru.md) и [матрицу](TEST-MATRIX.ru.md).

## 1. Зависимости

Выберите команды своей системы.

**Ubuntu / Debian**

```sh
sudo apt update
sudo apt install -y python3 nftables iproute2 ca-certificates
```

**Rocky Linux**

```sh
sudo dnf install -y python3 nftables iproute ca-certificates
```

**Alpine Linux от root**

```sh
apk add python3 nftables iproute2 coreutils ca-certificates
```

Проверьте интерпретатор службы.

```sh
/usr/bin/python3 --version
```

Требуется `/usr/bin/python3` версии 3.10 или новее. Python в другом пути или виртуальном окружении не меняет интерпретатор службы. Установщик проверяет конфигурацию и возможности nftables, в том числе динамические наборы и ограничения соединений. Используйте модули работающего ядра. Agent устанавливает собственную службу политики.

## 2. Распаковка и настройки

Загрузите `proxy-guard-source-0.3.0-21-pro-0.3.1-5.tar.gz` на VPS. В каталоге архива выполните:

```sh
tar -xzf proxy-guard-source-0.3.0-21-pro-0.3.1-5.tar.gz
cd Proxy-Guard/companion/vps
cp agent.example.json agent.json
chmod 600 agent.json
python3 - <<'PY'
from pathlib import Path
import json
import secrets

path = Path('agent.json')
config = json.loads(path.read_text())
config['agent_secret'] = secrets.token_urlsafe(32)
path.write_text(json.dumps(config, indent=2) + '\n')
path.chmod(0o600)
PY
```

| Параметр | Значение |
| --- | --- |
| `device_id` | Идентификатор, например `home`, общий для роутера и используемого Worker. |
| `agent_secret` | Отдельный случайный секрет, соответствующий `AGENT_SECRET` Worker. На роутер его не передают. |
| `services` | Имена реальных процессов и слушающие TCP/UDP-порты прокси. |
| `managed_units` | Зависимости запуска `name.service`. В OpenRC имя без `.service`. SSH исключён. |
| `egress.panel_config_path` | Необязательный доверенный локальный JSON Xray. Внешнее измерение по умолчанию выключено. |
| SSH, сигнал пути, обслуживание | Настроить и включить отдельно. |

Agent работает с уже установленным прокси. Для Xray под 3x-ui проверьте фактическое имя процесса и поддержку USR1 в этой версии, затем выберите адаптер.

## 3. Канал управления

### Cloudflare Worker и Tunnel/VPC

Обычно оставляют `bind=127.0.0.1`, `port=8788` и `public_control=false`. Локальный `cloudflared` обращается к loopback. Настройте Tunnel, VPC Service и `VPS_API` по [руководству Worker](CLOUDFLARE-WORKER.ru.md). Используйте общий `DEVICE_ID`, независимый `DEVICE_TOKEN` между устройством и Worker и `AGENT_SECRET` между Worker и Agent. На роутере выберите Cloudflare и укажите базовый HTTPS URL Worker, ID и токен устройства.

### Прямой HTTPS

Укажите `public_control=true`, адрес прослушивания, действительные `tls_cert`, `tls_key` и отдельный `direct_token`. На роутере выберите прямой HTTPS и укажите базовый URL Agent, ID и `direct_token`. Секреты состоят из 32–256 букв, цифр, подчёркиваний или дефисов. Замените примерные значения.

**Убедитесь, что управление идёт напрямую в обоих вариантах.** Независимый сигнал пути должен идти через локальный SOCKS.

<a id="control-and-path"></a>

### Адреса, секреты и независимый путь через прокси

| Назначение | На роутере | На сервере |
| --- | --- | --- |
| Cloudflare | HTTPS URL Worker, ID и токен устройства | `DEVICE_ID`, `DEVICE_TOKEN`. `AGENT_SECRET` совпадает с `agent_secret` Agent. |
| Прямой HTTPS | HTTPS URL Agent, ID и токен | `device_id`, `direct_token`, публичный слушатель и TLS. |
| Сигнал пути | Включённое наблюдение пути, HTTPS URL Agent, отдельный ключ | `path_token`. SOCKS к `/v1/direct/path-heartbeat`. |

В базовом URL опустите `/v1/...`. Храните секреты раздельно. Для управления SSH сначала подтвердите аутентификацию обоих путей.

- Прямое управление требует видимого реального публичного IP домашней сети. Agent не извлекает его из заголовков пересылки. Тот же HTTPS URL может принять сигнал через SOCKS с отдельным ключом.
- В Cloudflare локальный HTTP API обслуживает Tunnel. Для сигнала через прокси нужен отдельный доступный HTTPS-вход. Через обратный прокси TLS перенаправляйте только `/v1/direct/path-heartbeat` с сохранением Bearer. Прямое управление по-прежнему требует исходный IP.
- При публичном HTTPS на Agent включите публичный режим, токен и сертификаты и согласуйте протокол и порт Tunnel/VPC. Выпуск, продление сертификатов и настройка обратного прокси выполняются отдельно.

Входы управления и сигналов должны быть доступны до продления разрешения. Проверьте прямой и SOCKS-маршруты по отдельности.

## 4. Установка и проверка

Выполняйте из `companion/vps`.

**Ubuntu / Debian / Rocky Linux**

```sh
python3 agent.py --config "$PWD/agent.json" --check-config
sudo python3 agent.py --config "$PWD/agent.json" --check-kernel
sudo sh ./install.sh --install "$PWD/agent.json"

sudo systemctl status proxy-guard-access-policy proxy-guard-access --no-pager
sudo journalctl -u proxy-guard-access -n 50 --no-pager
```

**Alpine Linux от root**

```sh
python3 agent.py --config "$PWD/agent.json" --check-config
python3 agent.py --config "$PWD/agent.json" --check-kernel
sh ./install.sh --install "$PWD/agent.json"

rc-service proxy-guard-access-policy status
rc-service proxy-guard-access status
```

Программа находится в `/opt/proxy-guard-access`, действующая конфигурация в `/etc/proxy-guard-access/agent.json`. Установщик запускает Agent и службу политики и сохраняет прежнюю конфигурацию. Для изменения редактируйте действующую конфигурацию и проверяйте её заново. Сохраните и примените в LuCI, проверьте синхронизацию, разрешение и службы, выберите управляемые порты.

## 5. Аварийный SSH и порты панели

Управление SSH выключено по умолчанию. После включения, проверки рабочего сеанса и обоих путей, доступ открывается при непрерывной потере обоих аутентифицированных сигналов. Задержка по умолчанию **60 секунд**.

В новых конфигурациях аварийный доступ публичный по умолчанию. `0` действует до восстановления домашней авторизации, `30`–`3600` задаёт срок. Можно ограничить источниками управления. Прежнее явное значение, в том числе `600`, сохраняется. Публичный доступ увеличивает период экспозиции. По окончании срока новый SSH-сеанс может не открыться, если домашний IP сменился и нет разрешённого источника. Продолжают действовать системный экран, SSH и группы провайдера.

Отдельные невыбранные порты 3x-ui, API и подписок остаются под системным экраном. Выбранные и общие IP, протокол и порт фильтруются правилом. Проверьте реальные слушатели.

## 6. Режимы портов и конфигурация

Правило наследует режим или выбирает список допуска, стандартные ограничения либо наблюдение. Источники, пороги и сроки задаются отдельно. Клиент проверяет возможности до применения. Новые функции могут потребовать обновить Agent и при Cloudflare также Worker. Два редактора роутера меняют UCI локальной защиты и VPS, а слушатели, TLS и разрешения обслуживания задаются в Agent. См. [Worker](CLOUDFLARE-WORKER.ru.md).

## 7. Обновление и резервные копии

Сохраните SSH или консоль. Закрыто скопируйте действующую конфигурацию, TLS-сертификаты и ключи, совместимые исходники, настроенное постоянное состояние и журнал операций. Состояние и ревизии принадлежат своему экземпляру.

Запустите установщик из нового `companion/vps`. Первая строка для systemd, вторая для Alpine от root.

```sh
# Ubuntu / Debian / Rocky Linux
sudo sh ./install.sh --install /etc/proxy-guard-access/agent.json

sh ./install.sh --install /etc/proxy-guard-access/agent.json
```

Установщик проверяет конфигурацию и ядро, обновляет программу и службы и перезапускает Agent. Сверьте службу, аутентификацию, ревизию, возможности и порты. Перед откатом версии проверьте совместимость состояния и конфигурации.

## 8. Сквозная проверка

- Проверьте Agent, службу политики, реальный процесс и TCP/UDP-порты, а затем настоящий запрос прокси.
- Сверьте TLS, ID, отдельные секреты, прямой маршрут, а для Cloudflare также фиксированный VPC и Tunnel. Новый домашний IP нужно наблюдать и синхронизировать. Проверьте свежее разрешение в LuCI.
- Начните с одного пробного правила. Проверьте разрешённый и ограниченный источник, невыбранный порт, панель, подписку, SSH и Docker отдельно.
- Проверьте сигналы, спасение и обслуживание по отдельности. Сверьте правила при потере управления и прокси, истечении пробной политики и после перезагрузки.

| Симптом | Проверить |
| --- | --- |
| Предварительная проверка не прошла | Python, запущенный init, выражения nftables и модули. |
| HTTPS или аутентификация не работают | Цепочка и срок сертификата, часы, слушатель, ID и токен. Оставьте проверку TLS. |
| Worker отвечает, Agent недоступен | Tunnel, фиксированная цель, ID привязки, loopback Agent. |
| Управление работает, сигнал пути нет | Независимый HTTPS-вход, ключ пути, SOCKS и реальный выход. |
| Ограничены панель или подписка | Выбранные правила или общий IP/протокол/порт. |
| Аварийный доступ активен, SSH недоступен | Служба SSH, вход, системный экран и группы провайдера. |
| Настройки изменились, статус нет | Действующий файл, проверка и перезапуск, пробная политика или неизвестный результат. |

См. [архитектуру Pro](PRO-COMPANION.ru.md) и [восстановление](RECOVERY.ru.md).

## 9. Удаление

Из сохранённого `companion/vps` нужной версии выполните первую строку для systemd или вторую от root для Alpine.

```sh
sudo sh ./uninstall.sh --remove

sh ./uninstall.sh --remove
```

Удаляются службы и правила компонента. Конфигурация, секреты и программы сохраняются. См. [восстановление](RECOVERY.ru.md).
