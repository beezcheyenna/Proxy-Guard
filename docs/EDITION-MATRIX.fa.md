## ارتقای مستقل

Pro حداقل نسخهٔ استاندارد و API پایه را می‌سنجد. اگر هر دو سازگارند فقط Pro را ارتقا دهید. اصلاح‌های امنیت، وضعیت و سازگاری فریم‌ور استاندارد به ارتقای استاندارد نیاز دارند. Pro صفحات پنج‌زبانه، تأیید سیاست و ویرایشگر خام خود را دارد.

اگر ابتدا استاندارد ارتقا یابد، اسکریپت آن ورودی ترجمهٔ لازم برای Pro قدیمی نصب‌شده را حفظ می‌کند. Pro جدید آن فهرست موقت را حذف می‌کند. قابلیت Agent و Worker جداگانه بررسی می‌شود و قابلیت جدید ممکن است به ارتقای هر دو نیاز داشته باشد.

## دامنهٔ فعلی

نصب تازه محافظت استاندارد و Pro را خاموش می‌گذارد. SSH و نگهداری جداگانه مجاز می‌شوند. کشف پورت فقط پیشنهاد می‌دهد و پورت انتخاب‌نشده تابع فایروال سیستم است. کنترل و همگام‌سازی IP خانگی پیش‌فرض IPv4 هستند. مسیر دادهٔ IPv6 جداگانه بررسی می‌شود.

استقرار بر یک شناسهٔ روتر و Agent متمرکز است. ساختار و کلاینت خود را بسنجید. دسته‌بندی دقیق fallback دادهٔ ساخت‌یافتهٔ مورد اعتماد می‌خواهد. پس از فرایند، پورت و گزارش شروع، درخواست واقعی پروکسی را بررسی کنید. [سازگاری](COMPATIBILITY.fa.md) را ببینید.

## حداقل سازگاری این انتشار

| مؤلفه | انتشار یا شناسه | شرط |
| --- | --- | --- |
| استاندارد IPK | 0.3.0-21 | LuCI، opkg، firewall4/nftables و وابستگی متناظر |
| Pro IPK | 0.3.1-5 | استاندارد **≥ 0.3.0-13**، **API 1** پایه |
| استاندارد APK | 0.3.0-r21 | SDK متناظر، apk، LuCI و firewall4/nftables |
| Pro APK | 0.3.1-r5 | استاندارد **≥ 0.3.0-r20**، **API 1** پایه |
| عامل VPS | **v3** | پروتکل کنترل، قابلیت و پاسخ تأیید بررسی می‌شوند |
| پروژهٔ npm Worker | **0.2.0** | پاسخ v3 را عبور و بررسی می‌کند. نسخهٔ npm مربوط به ابزار است |

وابستگی و API در [package/Makefile](../package/Makefile) مشخص‌اند. IPK و APK قالب نسخهٔ خود را دارند. حداقل، شرط نصب است. Agent و Worker اختیاری را از [منبع انتشار متناظر (انگلیسی)](https://github.com/beezcheyenna/Proxy-Guard/releases/tag/v0.3.0-21-pro-0.3.1-5) بگیرید و برچسب یا commit استقرار را ثبت کنید. کد Worker مستقرشده را جدا از `package.json` بررسی کنید.

### انتخاب مؤلفه‌های ارتقا

| تغییر | اقدام | هنگام ناسازگاری |
| --- | --- | --- |
| رابط، ترجمه یا اصلاح Pro در API 1 | با پایهٔ سازگار فقط Pro ارتقا یابد | پایهٔ ناسازگار در نصب یا شروع رد می‌شود |
| اصلاح استاندارد با حفظ API 1 | فقط استاندارد ارتقا یابد | API اصلی تازه جداگانه بررسی شود |
| قانون پورت، حالت مبدأ یا اجرای آزمایشی | ابتدا Agent و در Cloudflare، Worker هم ارتقا و بررسی شوند | نبود `per_rule_modes`، `source_modes_v2` یا `policy_confirmation` اعمال را رد می‌کند |
| پروتکل یا پاسخ رله ناسازگار | منبع متناظر و آزمون انتهابه‌انتها. HTTPS مستقیم به Agent می‌رود | خطا را ثبت و سیاست واقعی را بررسی کنید |
| واردکردن خروجی VPS | طرح ۱ در Agent و مسیر کنترل لازم است | نامزد نامعتبر رد می‌شود و بررسی اتصال استاندارد ادامه دارد |

برای Pro استاندارد سازگار را نگه دارید. با خطای اعمال، قانون‌های قبلی ممکن است بمانند. شمارهٔ بازبینی، تأیید در انتظار و قانون واقعی را طبق [بازیابی](RECOVERY.fa.md) بسنجید.
