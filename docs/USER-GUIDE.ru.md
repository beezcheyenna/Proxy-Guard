<a id="guide-setup"></a>

## Установка и первоначальная настройка

1. Установите подходящий IPK Standard через страницу пакетов LuCI. Для функций VPS добавьте совместимый пакет Pro.
2. Откройте «Службы → Proxy Guard», пройдите мастер и проверьте SOCKS, клиент, входные интерфейсы, область IPv4 / IPv6 и исключения. Сначала включите проверки в режиме «Только наблюдение», сохраните и примените настройки, подтвердите по запросу и проверьте результаты.
3. Когда будете готовы к блокировке, выберите режим защиты и снова нажмите «Сохранить и применить». После успешной самопроверки **подтвердите в течение 30 секунд**. При ошибке самопроверки или отсутствии подтверждения настройки откатываются. Обычный сбой прокси обрабатывается процедурой защитной блокировки.

После установки защита, проверка выходного IPv4 и расписание отключены. Редактирование меняет черновик; «Сохранить» сохраняет его, а **«Сохранить и применить» отправляет изменения**. В настройках можно повторить мастер, загрузить последнюю подтверждённую конфигурацию или редактировать исходную UCI.

## Требования и область защиты

<a id="guide-requirements"></a>

### Какие системы и прокси-клиенты поддерживаются?

Маршрутизатору нужны **opkg + LuCI + firewall4/nftables**, а также Lua, ucode, curl и другие зависимости из репозиториев, соответствующих прошивке. Проверенные на совместимость сборки включают OpenWrt `24.10.4`, ImmortalWrt `24.10.4` и iStoreOS `24.10.8`.

Предусмотрены адаптеры PassWall, PassWall2, OpenClash, Nikki и HomeProxy. Поддержка зависит от версии клиента, ядра прокси и режима перенаправления. Некоторые сочетания sing-box redirect / HomeProxy TUN имеют ограничения; изучите [таблицу совместимости](COMPATIBILITY.md). IPK не поддерживает прошивки с APK и системы только с fw3/iptables. Обозначение `all` не означает, что проверены все архитектуры и устройства.

Linux Agent для Pro требует Python `3.10+`, nftables и соответствующих возможностей ядра. Поддерживаются systemd / OpenRC. Для определённых выпусков Ubuntu, Debian, Rocky Linux и Alpine Linux выполнены проверки совместимости. См. [установку в Linux](LINUX-AGENT-INSTALL.md).

<a id="guide-scope"></a>

### Какой трафик защищается и каковы ограничения топологии?

- **Блокируется только трафик, проходящий через этот маршрутизатор.** При размещении шлюза без NAT в одной подсети обратный трафик может идти в обход. Его перехватить нельзя. Устройства, использующие другой шлюз и лишь проходящие через коммутатор этого устройства, не входят в защищаемый маршрут.
- Для выбранных устройств или подсетей защита может охватывать IPv4/IPv6 и TCP/UDP в обоих направлениях, включая установленные соединения, если трафик реально проходит через маршрутизатор. Соединения, инициированные самим маршрутизатором, не входят в область защиты этих клиентов.
- Плагин не меняет NAT, интерфейсы, системные маршруты, DNS и настройки прокси-клиента. Сохранение LAN, DNS и управления требует правильных областей и исключений.
- Ускорение потоков, мостовая фильтрация или недостаточные возможности ядра могут препятствовать включению защиты. Аппаратное ускорение производителя, физические интерфейсы, несколько входов, VPN и контейнеры проверяются на реальном устройстве.
- Одна успешная проверка не доказывает работоспособность всех сайтов, UDP-приложений и выходов IPv6. Интервалы опроса, неподдерживаемые сообщения и новые версии исходных проектов ограничивают обнаружение.
- Перед включением защиты проверьте фактическую топологию и пути трафика. Начните с одного клиента: проверьте блокировку при сбое, восстановление, LAN, DNS, управление и устройства с другим шлюзом, затем расширяйте область.

### Что нужно для Pro и можно ли обновлять его отдельно?

Для Pro нужны совместимый Standard и отдельно установленный Linux VPS Agent. Канал управления может использовать прямой HTTPS или Cloudflare; установка расширения не создаёт облачные ресурсы. При совместимых интерфейсах Pro обновляется отдельно. Исправления безопасности, автомата состояний, совместимости прошивки или общих переводов в Standard могут потребовать его обновления.

<a id="advanced-settings"></a>

## Настройка и работа

<a id="guide-options"></a>

### Как выбрать основные настройки

| Настройка | Что указать |
| --- | --- |
| Режим работы | В режиме наблюдения плагин проверяет и записывает результаты, но не блокирует трафик. Режим защиты ограничивает его при сбое или по расписанию. |
| Локальный SOCKS | Укажите реальный локальный порт SOCKS5 вашего прокси-клиента. Значение `1070` — пример; плагин не создаёт прокси. |
| Входной интерфейс | Выберите устройство уровня L3, через которое входит защищаемый трафик, например LAN-мост с маршрутизацией. Не выбирайте все физические порты без проверки. |
| Защищаемые адреса | Укажите реальные IPv4-адреса устройств или подсети и отдельно подтвердите IPv6. Выбор одного IPv4-устройства не охватывает автоматически все его IPv6-адреса. |
| Исключения LAN | Добавляйте только необходимые локальные сети, включая нужные сервисы в других подсетях. Слишком широкие исключения ослабляют защиту. |
| Входные порты прокси и DNS | Укажите реальные порты. Правила входа прокси предотвращают обход через явно заданный прокси; исключения DNS должны соответствовать фактическим портам назначения. Списки не должны пересекаться. |
| Проверка выходного IPv4 | По умолчанию отключена. При включении задайте доверенный ожидаемый адрес; не считайте любой новый обнаруженный адрес доверенным автоматически. |
| Контроль служб, журналов и защита при загрузке | В сохранённой конфигурации новой установки эти функции отключены. Мастер может предложить контроль служб для обнаруженного клиента; проверьте сводку и применённые настройки. Для защиты при загрузке также нужны основной переключатель, режим защиты и контроль служб. |
| Защита по расписанию | По умолчанию отключена, готового расписания нет. Перед применением проверьте время, дни повторения и фиксированное смещение UTC. |

Задавайте по одной HTTPS-цели на строку в формате `https://узел/путь|ожидаемый_код`, например `https://www.gstatic.com/generate_204|204`. Число `204` после разделителя — ожидаемый HTTP-код, а не часть URL. Можно задать 2–4 цели и минимальное число успешных проверок за цикл в обычном режиме; по умолчанию достаточно 1. При усиленном наблюдении должны успешно пройти проверки всех целей. Запросы идут через локальный SOCKS, поэтому сбой или ограничение частоты на целевом сайте тоже влияет на результат.

При включённой проверке выходного адреса обычные запросы по умолчанию используют ipify. Дополнительная проверка Cloudflare выполняет одну попытку после первой готовности прокси при загрузке и одну после восстановления каждого прерывания. Сигналы одного прерывания объединяются; ежедневного или непрерывного опроса нет. Эта функция также зависит от включения проверки выходного адреса. Не добавляйте Cloudflare trace в список частых проверок: постоянная доступность и отсутствие ограничений частоты не гарантируются ни для одного стороннего API.

Тайм-аут или недоступность Cloudflare сами по себе не вызывают блокировку; обычные проверки всё равно должны пройти. Если полученный выходной адрес отличается от ожидаемого, это считается сбоем.

**Рекомендуемый порядок первичной проверки:**

1. Начните с одного устройства под вашим управлением. Проверьте шлюз, пути IPv4 / IPv6 и исключения для LAN, DNS и управления.
2. Включите режим наблюдения, сохраните и примените настройки, подтвердив их при запросе. Проверьте результаты запросов к сайтам, необязательную проверку выхода и включённый контроль служб клиента.
3. Переключитесь в режим защиты, сохраните и примените. После успешной самопроверки подтвердите в течение 30 секунд, сохранив отдельный доступ для управления или консоль.
4. В контролируемое окно обслуживания воспроизведите сбой и восстановление прокси. Проверьте новые и установленные соединения по нужным путям IPv4 / IPv6 и TCP / UDP, а также LAN, DNS, управление и устройства с другим шлюзом.
5. Затем расширяйте охват и добавляйте расписание или защиту при загрузке. Последнюю проверяйте отдельной перезагрузкой; самопроверка не заменяет проверку реального трафика.

<a id="guide-detection"></a>

### Проверки, блокировка и восстановление

#### Обычные проверки соединения

Проверки соединения всегда идут через настроенный локальный SOCKS, без перехода на прямое соединение. Сверка выходного IPv4 по умолчанию выключена. Для её включения нужен доверенный ожидаемый адрес. Pro может получить адреса-кандидаты с VPS, но адрес интерфейса или панели не обязательно совпадает с фактическим выходом прокси. Проверьте выбор, сохраните и примените его.

По умолчанию обычная проверка начинается через 10 секунд после завершения предыдущего цикла; время запросов учитывается отдельно. Три неудачных цикла подряд подтверждают сбой, а два успешных — восстановление. Эти значения настраиваются. Обновление страницы примерно раз в секунду не означает, что обычная внешняя проверка выполняется каждую секунду.

Фиксированная задержка при запуске по умолчанию заканчивается через 150 секунд после загрузки роутера; в режиме защиты трафик всё это время заблокирован. Защита при загрузке заменяет этот срок ожиданием готовности необходимых служб, после чего выполняются настроенное ожидание с блокировкой и проверки восстановления.

#### Наблюдение за службами и журналами

При включённом наблюдении за службами клиента остановка или перезапуск любого отслеживаемого компонента TCP, UDP или DNS по умолчанию запускает защиту. Наблюдение за журналом включается отдельно в рамках наблюдения за службами и распознаёт поддерживаемые сообщения исходных проектов; язык интерфейса не меняет охват распознавания. Дополнительная проверка UDP требует поддержки SOCKS5 UDP ASSOCIATE.

Контроль служб учитывает компоненты, нужные текущей конфигурации клиента. Ненастроенные или ненужные UDP / DNS не считаются неисправными автоматически. Если клиент не распознан, проверьте адаптер и настройки; отсутствие проверки не подтверждает исправность.

#### Блокировка и восстановление

Если защиту запускает наблюдение за службами, восстановление по умолчанию проходит так:

1. **Блокировка и ожидание 15 секунд**. В это время внешние проверки не выполняются.
2. После ожидания и готовности служб выполняется новая проверка прокси. Трафик разрешается только при выполнении условий восстановления.
3. После открытия доступа начинается **60 секунд усиленного наблюдения**. При нормальной работе Интернет в этот период доступен. Новый обнаруженный сбой снова блокирует трафик и запускает ожидание.

При усиленном наблюдении следующий цикл начинается примерно через секунду после завершения предыдущего; время запросов добавляется отдельно. Проверки всех HTTPS-целей, а также включённые проверки выходного IPv4 и UDP должны завершиться успешно. Любая неудача снова блокирует трафик без применения обычного минимума успешных целей или порога последовательных неудач.

Ожидание, усиленное наблюдение и их длительность настраиваются. После сбоя, обнаруженного по журналу, первое восстановление пропускает дополнительное ожидание лишь после свежего сообщения о завершении запуска, восстановления служб и новой проверки прокси. Завершение окна расписания использует тот же порядок только при включённом наблюдении за службами и отсутствии другого сбоя или незавершённого ожидания. Новый сбой во время усиленного наблюдения снова блокирует трафик и запускает ожидание. Защита при загрузке включается отдельно. См. [порядок проверок](USAGE.md) и [совместимость журналов](LOG_COMPATIBILITY.md).

<a id="guide-schedule"></a>

### Расписание, состояние и языки

#### Расписание

После новой установки защита по расписанию выключена, **время и дни недели не заполнены**. Можно выбрать ежедневное повторение или несколько дней недели. Интервал через полночь относится ко дню начала. Используется фиксированное смещение UTC, по умолчанию `UTC+00:00`, без автоматического перехода на летнее время. При обновлении сохраняются выбранное смещение UTC и расписание.

Например, выбор только понедельника с началом в `22:00` и окончанием в `06:00` означает блокировку с вечера понедельника до утра вторника в выбранном смещении UTC. Дополнительно выбирать вторник не нужно. Пример не создаёт расписание автоматически. Блокируется только интернет-трафик выбранных клиентов; LAN, DNS и управление сохраняются согласно исключениям.

#### Состояние и журналы

Страница автоматически обновляет состояние, события и подробности проверок. Контроль процессов и ограниченное автоматическое восстановление предназначены для сбоев самого плагина; неисправности прокси обрабатываются процедурой защиты. Журналы плагина хранятся в памяти и теряются при перезагрузке. Отдельно настроенное постоянное системное журналирование от этого параметра не зависит.

#### Языки интерфейса

Интерфейс следует языку LuCI и поддерживает **упрощённый китайский, английский, японский, русский и персидский**. Язык инструкции можно выбрать вверху страницы.

<a id="guide-troubleshooting"></a>

#### Как понимать состояние

| Состояние или сообщение | Значение и действие |
| --- | --- |
| Отключено | Плагин не обеспечивает блокировку. Проверьте основной переключатель и применённые настройки. |
| Только наблюдение | Проверки идут без ограничения доступа. Ошибки в журнале не приводят к установке блокирующей политики. |
| Заблокировано или действует расписание | Проверьте причину, расписание и состояние служб. Предупреждение может означать правильную реакцию на сбой. |
| Обратный отсчёт ожидания | Интернет остаётся заблокированным, внешние проверки ещё не начались. После ожидания проверки восстановления всё равно должны пройти. |
| Доступ восстановлен, усиленный контроль | При исправной работе доступ разрешён. Новый сбой снова блокирует его и запускает ожидание. |
| Ожидание интерфейса LAN | Проверьте выбранное имя и фактическое состояние интерфейса. Плагин не создаёт и не включает интерфейсы. |
| Устаревшие данные, нет связи или правила не подтверждены | Защита сейчас не подтверждена. Сохраните ошибку и проверьте процессы, правила и настройки, не полагаясь на прежний зелёный индикатор. |

#### Обновление, переустановка и диагностика

Перед обновлением сохраните настройки плагина. Отдельно и безопасно скопируйте секреты сопряжения Pro, закрытую конфигурацию Agent и сертификаты. Обновление сохраняет выбранные значения, не заменяя их новыми значениями по умолчанию. При установке исправленного пакета с той же версией opkg может считать его уже установленным. Проверьте источник и контрольную сумму, затем используйте процедуру переустановки той же версии из [инструкции по установке](USAGE.md#安装升级和卸载); не обходите проверку зависимостей. Независимое обновление Pro требует совместимого базового API; новые удалённые функции могут потребовать обновления Agent или Worker.

Если нет меню, страница работает неправильно или RPC-объект не найден, сохраните полный вывод установки, затем заново войдите в LuCI и обновите страницу. При нормальной установке обработчики пакета очищают кэш и перезагружают регистрацию RPC. Если повторный вход не помог, проверьте ошибки установки и зависимости; не расширяйте ACL и не считайте ручную перезагрузку службы доказательством успешной установки.

Проверки только для чтения на своём маршрутизаторе:

```sh
opkg status luci-app-proxy-guard
/usr/libexec/proxy-guard status
/usr/libexec/proxy-guard logs
```

Очистка журналов удаляет только журналы плагина, не исходный журнал клиента и не блокировку. Для снятия защиты выключите основной переключатель, сохраните и примените. Завершение процессов или удаление пакета не является безопасным способом временно разрешить доступ. Перед отправкой диагностики удалите реальные адреса, секреты, ссылки подписок и заголовки авторизации. Об уязвимостях сообщайте приватно по адресу ниже.

<a id="guide-pro"></a>

### Pro: доступ к VPS, SSH и удалённое обслуживание

Pro синхронизирует аутентифицированный домашний публичный IP и применяет правила выбранных портов служб VPS. Исправность служб VPS может быть дополнительным условием восстановления доступа; локальные проверки прокси всё равно должны пройти. Необязательное ограничение полосы применяется только к соединениям fallback, подтверждённым доверенной телеметрией.

#### Порты и политики

Pro управляет только локальными сервисными портами VPS, которые вы явно добавили и включили. Обнаружение слушающих портов лишь предлагает кандидатов. Остальные порты остаются под управлением существующего межсетевого экрана. Перенаправляемые порты Docker и все порты машины автоматически не включаются.

Для каждой записи доступны **только разрешённые адреса, стандартная защита от злоупотреблений или только наблюдение**. Источники, пороги соединений и интервалы задаются отдельно. Изменения удалённой политики имеют собственный срок подтверждения — **60 секунд по умолчанию**. Без подтверждения восстанавливается прежняя политика. Панель, API или подписка на том же выбранном порту, что и прокси, тоже могут попасть под ограничения.

Режим работы и выбор источников — разные настройки. Все источники в стандартном режиме по-прежнему подпадают под ресурсные ограничения; прежний вариант без ограничений полностью обходит защиту порта. Режим только белого списка нельзя сочетать со всеми источниками. Освобождение домашнего IP или статического белого списка от стандартных ограничений зависит от выбранного типа источников правила.

Режим наблюдения не блокирует выбранные сервисные порты. Отдельно включённое управление SSH продолжает действовать по собственным настройкам.

#### Аварийный доступ по SSH

SSH по умолчанию не управляется, удалённое обслуживание выключено. Если включить управление SSH, потеря обоих каналов аутентифицированных сигналов активности (heartbeat) на заданное время (по умолчанию 60 секунд) может включить аварийный доступ. В новой конфигурации аварийный доступ по умолчанию открыт из Интернета до восстановления домашней авторизации. Можно задать срок или ограничить источники управления. Постоянное открытие увеличивает время доступности SSH извне; истечение срока без подходящего разрешённого источника может помешать новому входу. Аутентификация SSH, системный межсетевой экран и внешние группы безопасности продолжают действовать.

#### Канал управления

Для управления можно использовать прямой HTTPS либо Cloudflare Worker с Tunnel/VPC. Канал служит для аутентификации и согласования политик, а не для передачи прокси-трафика. Запросы управления должны обходить прокси; прямой маршрут необходимо настроить и подтвердить самостоятельно. Плагин не меняет маршруты и правила разделения трафика. Независимый heartbeat по пути прокси, напротив, проходит через локальный SOCKS и проверяет этот путь. По умолчанию управление использует IPv4. Фильтрация IPv6-трафика не означает, что облачное управление по IPv6 проверено. См. [компоненты Pro](../companion/README.md).

Независимому пути через прокси нужны отдельный секрет heartbeat и HTTPS-вход Agent. В режиме прямого HTTPS можно использовать тот же базовый URL Agent, но управление должно идти напрямую, а проверка пути — через SOCKS. В режиме Cloudflare адрес Worker не заменяет независимый вход. См. [соответствие настроек соединения](LINUX-AGENT-INSTALL.md#control-and-path).

#### Фиксированные операции обслуживания

Удалённое обслуживание по умолчанию отключено. Для запроса перезагрузки VPS или перезапуска поддерживаемого ядра Xray действие нужно разрешить и на маршрутизаторе, и в VPS Agent. Принятый запрос не означает завершённого восстановления: проверьте последующие результаты. Произвольные удалённые команды не предоставляются.

#### Первая установка Pro

1. Проверьте локальную защиту обычной версии, затем установите совместимое расширение Pro.
2. Установите Agent на выбранный Linux VPS. Проверьте реальные службы, порты, зависимости и действующий межсетевой экран, сохранив доступ по SSH или через консоль.
3. Выберите прямое HTTPS-управление или Cloudflare и отдельно настройте нужные учётные данные. Убедитесь, что управляющие запросы обходят прокси. Для аварийного SSH также настройте независимую проверку связи по HTTPS через прокси.
4. Сначала проверьте аутентификацию, выданные разрешения и состояние служб. Обнаружение слушающих портов только предлагает варианты. Добавляйте лишь нужные порты и проверяйте, не используют ли панель, подписки или SSH тот же вход.
5. Сохраните и примените настройки, проверьте результат пробной политики на VPS и подтвердите до удалённого срока — по умолчанию 60 секунд. Это отдельный процесс, не локальное 30-секундное подтверждение обычной версии.
6. Управление SSH, дополнительное условие исправности VPS и удалённое обслуживание включайте по необходимости, проходя соответствующие проверки отдельно. Остановка синхронизации не удаляет правила VPS; для удаления предусмотрены подготовка, применение и подтверждение.
