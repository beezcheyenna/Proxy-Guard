# Установка и использование

[English](USAGE.en.md) · [简体中文](USAGE.md) · [日本語](USAGE.ja.md) · [Русский](USAGE.ru.md) · [فارسی](USAGE.fa.md)

Установите Proxy Guard на маршрутизатор с LuCI и firewall4/nftables. Выберите формат пакета, который использует ваша прошивка.

## Загрузка и проверка

Скачайте пакет и контрольные суммы из одного релиза. Для opkg выберите IPK, для apk — APK. Установите зависимости из источников, соответствующих вашей прошивке.

[GitHub Releases](https://github.com/beezcheyenna/Proxy-Guard/releases)

Укажите имя скачанного файла. Первая строка выбирает IPK. Для APK используйте имя из комментария в следующей строке.

```sh
PG_PACKAGE=luci-app-proxy-guard_1.0.0-8_all.ipk
# PG_PACKAGE=luci-app-proxy-guard-1.0.0-r8.apk
awk -v f="$PG_PACKAGE" '$2 == f { print; n++ } END { if (n != 1) exit 1 }' SHA256SUMS > SHA256SUMS.selected &&
sha256sum -c SHA256SUMS.selected
```

Проверка должна показать OK для выбранного файла. В macOS можно выполнить `shasum -a 256 "$PG_PACKAGE"` и сравнить полную сумму с соответствующей строкой в `SHA256SUMS`.

SHA256 проверяет целостность по списку. Издателя проверяйте отдельно, а файл и список берите из одного доверенного релиза. Для автономной установки на прошивке с apk заранее установите подходящие зависимости.

<a id="installation"></a>

## Установка и удаление

Выберите команды для своей прошивки. В примере установки APK параметр `--no-network` отключает доступ к сети. Зависимости должны быть уже установлены или доступны в локальном репозитории. Чтобы получить недостающие зависимости из настроенных репозиториев для вашей прошивки, уберите `--no-network`. На время проверки защиты сохраните отдельный канал управления.

```sh
opkg install /tmp/luci-app-proxy-guard_1.0.0-8_all.ipk
apk --no-network --allow-untrusted add /tmp/luci-app-proxy-guard-1.0.0-r8.apk
```

```sh
opkg remove luci-app-proxy-guard
apk --no-network del luci-app-proxy-guard
```

<a id="from-0-3"></a>

## Переход с 0.3 на 1.0

Настройте 1.0 заново. Обновление опубликованных пакетов 0.3 до 1.0 поверх установленной версии и откат с 1.0 до 0.3 не проверены как поддерживаемые способы перехода. В обоих пакетах `/etc/config/proxy_guard` объявлен файлом конфигурации, поэтому менеджер пакетов может сохранить изменённый файл версии 0.3. Установщик обновляет некоторые известные значения по умолчанию для проверок и дополняет отдельные отсутствующие параметры. Проверьте сохранённые настройки перед их использованием в 1.0.

Сохраните отдельный способ управления роутером. Создайте резервную копию конфигурации 0.3 и храните учётные данные и соответствующие пакеты в защищённом месте. Явно отключите защиту старой версии. Если установлен Pro, сначала разберитесь с политикой VPS по инструкции ниже и удалите Pro. Удалите 0.3 Standard, затем установите 1.0. Если старые настройки остались, выберите «Настройка и диагностика → Восстановить настройки по умолчанию и настроить заново». Повторно введите только проверенные границы защиты, исключения, параметры SOCKS и расписания.

При чистой установке 1.0 используется официальный HTTPS, а сверка выходного IPv4 выключена. Если в сохранённой старой конфигурации не указан способ проверки, 1.0 использует официальный HTTPS. Чтобы и дальше проверять gstatic и Ubuntu, выберите сторонний HTTPS в настройках проверки соединения.

Если 0.3 Pro управляет VPS, отмените ненужную политику через 0.3 Pro, пока есть доступ к управлению, и проверьте результат на VPS. В 1.0 нет встроенной интеграции с 0.3 Pro. Действующие правила на VPS, Agent и ресурсы Cloudflare обслуживаются отдельно. [Архивная инструкция по восстановлению](https://github.com/beezcheyenna/Proxy-Guard/blob/987ff38a25c1a00f2c05753f7503e134391a4a3a/docs/RECOVERY.ru.md)

[Исходный код, пакеты и документация 0.3](../archive/0.3/README.md)


<a id="guide-setup"></a>

## Первичная настройка

**После остановки службы Proxy Guard правила межсетевого экрана могут продолжить блокировку.** Чтобы снять её, явно отключите защиту или следуйте [инструкции по восстановлению](RECOVERY.ru.md).

**Успешная проверка текущего прокси подтверждает доступность только для этого запроса.** Расписание, запрос API или отдельная неудачная проверка могут по-прежнему блокировать доступ.

Откройте «Службы → Proxy Guard». Проверьте в мастере входные интерфейсы, область IPv4 и IPv6, локальные исключения и порт SOCKS. Сначала используйте режим наблюдения. После сохранения и применения пройдёт самопроверка. На подтверждение даётся 30 секунд. Если проверка не пройдена или подтверждения нет, настройки откатываются.

Официальная проверка HTTPS по умолчанию обращается к фиксированному адресу через локальный SOCKS. У сторонней проверки свои интервалы и пороги. Проверка исходящего IPv4 изначально выключена и после включения по умолчанию использует адрес из официального ответа. Резервный сторонний IP-сервис опрашивается только при тайм-ауте основного.

Официальная проверка HTTPS по умолчанию ждёт 3 секунды после завершения проверки, а тайм-аут запроса составляет 2 секунды. Сторонняя проверка ждёт 10 секунд после раунда, тайм-аут каждого запроса составляет 4 секунды. По умолчанию проверяются gstatic и Ubuntu, в обычном раунде достаточно одной успешной проверки. В обычном режиме защиты сбой подтверждается после двух неудачных официальных проверок или трёх неудачных сторонних раундов подряд. Для восстановления по умолчанию нужны две успешные проверки или два успешных раунда подряд. Во время усиленной проверки блокировку может вызвать один сбой.

Если оба текстовых сервиса IPv4 превысили время ожидания, такой результат сам по себе не вызовет блокировку при рабочем соединении и отсутствии неустранённого несовпадения. После тайм-аута у основного адреса `https://api.ipify.org/` используется `https://4.ident.me/`. Если у собственного основного адреса не настроен резервный, тайм-аут означает, что сверка недоступна. Тогда действуют настроенные режим и порог сбоев. После подтверждённого несовпадения для восстановления нужен ожидаемый IPv4.

Пока правила требуют проверки, кнопка подтверждения недоступна. Исходный отсчёт продолжается. По истечении времени маршрутизатор восстановит прежние настройки, даже если страница уже закрыта.

<a id="test-current-proxy"></a>

## Проверить текущий прокси

Кнопка «Проверить текущий прокси» использует несохранённые настройки формы и подключение через SOCKS. Она показывает результат, задержку и доступный исходящий IPv4. Кнопка «Запустить подробную диагностику» в том же окне использует уже применённые настройки прокси. Чтобы настройки защиты вступили в силу, сохраните и примените их.

В состоянии отображаются число последовательных неудачных проверок и действующие причины блокировки. При сбое ниже порога доступ может сохраниться. Расписание, запросы API и неполадки подключения могут действовать одновременно.

Локальный API при новой установке выключен. После включения UUID из LuCI позволяет получать статус, запускать диагностику и добавлять или отменять временные блокировки.

## Проверка защиты при запуске

Сохраните отдельный канал управления и перезагрузите маршрутизатор с Proxy Guard. На защищённом устройстве убедитесь, что при запуске маршрутизатора интернет-трафик блокируется и возобновляется после успешного прохождения настроенных проверок восстановления.

<a id="local-api"></a>

## Локальный API

Включите API на вкладке «API управления в локальной сети» в LuCI, нажмите «Сохранить и применить» и подтвердите настройки, если появится запрос. Скопируйте **UUID API** на той же вкладке. Передавайте `Authorization: Bearer YOUR_UUID` в каждом запросе.

**UUID служит учётными данными.** После выключения и повторного включения API, а также после перезагрузки роутера с включённым API, создаётся новый UUID. Обновите его в вызывающих программах. Для вызовов достаточно UUID API. UUID возвращается в ответе на принятый запрос и доступен администраторам в журнале событий LuCI. Скрывайте его перед публикацией ответов и журналов.

**Используйте текущий адрес управления роутером по HTTPS.** API принимает обращения с петлевого интерфейса или от узла, к которому есть прямой обратный маршрут через устройство в зоне межсетевого экрана с именем `lan`. Источники за другим шлюзом отклоняются. Другие зоны, маршрутизируемые VLAN и VPN могут получить `403 lan_required`. Используйте имя узла из сертификата. Для частного центра сертификации или самоподписанного сертификата укажите доверенный сертификат через параметр curl `--cacert`.

Замените `router.example` именем роутера для управления по HTTPS, а `YOUR_UUID` текущим UUID API. В JSON ниже используются примеры значений. Вызывайте POST, только если нужно изменить доступ в Интернет в настроенной области защиты.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | [`/status`](#api-status) | Получить состояние защиты |
| GET | [`/diagnostics`](#api-diagnostics) | Запустить разовую проверку |
| POST | [`/block`](#api-block) | Запросить временную блокировку |
| POST | [`/cancel`](#api-cancel) | Отменить временную блокировку |

<a id="api-status"></a>

### Получить состояние защиты

`GET /status` сообщает текущее состояние межсетевого экрана и действующие запросы блокировки через API. В примере уже активна временная блокировка. В программах используйте `enforcement` и `block_reasons`. Поле `reason` предназначено для отображения. Поле `last_check` содержит время последней завершённой проверки в секундах Unix и может отсутствовать, пока проверки не было. Поле `blocked` может быть опущено, если состояние неизвестно, правила отсутствуют или ещё не проверены. Эти состояния различайте по `enforcement`.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' 'https://router.example/cgi-bin/proxy-guard-api/status'
```

```json

  "enabled": true,

  "check_mode": "web",
  "phase": "blocked",
  "enforcement": "blocked",
  "blocked": true,
  "reason": "API 限时断网生效中",
  "block_reasons": [
    "api"
  ],
  "failure_progress": {
    "count": 0,
    "threshold": 3
  },
  "last_check": 1794628800,
  "stale": false,
  "heartbeat": {
    "enabled": false,
    "allowed": true
  },
  "api": {
    "enabled": true,

    "remaining": 95
  },

    {
      "request_id": "example-block-01",

  "exit_check": {
    "enabled": false
  }
}
```

<a id="api-diagnostics"></a>

### Запустить диагностику

`GET /diagnostics` запускает проверку через локальный SOCKS и возвращает её результат в том же ответе. В настройке «Адрес для обновления через API» по умолчанию выбран PGHB `/`. Для заголовков из примера выберите `/f` и примените настройку. [Описание ответа PGHB](PGHB.ru.md)

```sh
curl -H 'Authorization: Bearer YOUR_UUID' 'https://router.example/cgi-bin/proxy-guard-api/diagnostics'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "diagnostics": {
    "ok": true,
    "source": "https://hb.pghb.app/f",
    "checked_at": 1794628800,
    "http_code": 200,
    "curl_code": 0,
    "milliseconds": 117,
    "nonce_verified": true,
    "headers": [
      {
        "name": "x-pghb-ip",
        "value": "203.0.113.10"
      },
      {
        "name": "x-pghb-tls",
        "value": "TLSv1.3"
      },
      {
        "name": "x-pghb-nonce",
        "value": "0123456789abcdef0123456789abcdef"
      }
    ]
  }
}
```

В `diagnostics.headers` имена и строковые значения заголовков `X-PGHB-*` перечислены в порядке ответа. Повторы `X-PGHB-IP` или `X-PGHB-Nonce` приводят к ошибке проверки. Другие повторяющиеся заголовки могут возвращаться отдельными элементами. Для данных вне UTF-8 добавляется `"encoding":"base64"`. `checked_at` содержит время Unix в секундах.

<a id="api-block"></a>

### Запросить временную блокировку

Для `POST /block` нужен активный режим защиты. Запрос действует на настроенную область защиты. Значение по умолчанию 300 секунд, исходный максимум 3600 секунд. Отсутствующее или нулевое `seconds` использует настроенное значение по умолчанию. Если `request_id` не задан, роутер создаёт его сам. Указанный ID должен содержать 8–64 буквы латиницы, цифры, дефисы или подчёркивания. Повтор действующего ID с тем же сроком сохраняет исходное время окончания. Другой срок вызывает `409 request_conflict`.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' \
  -H 'Content-Type: application/json' \
  --data '{"seconds":120,"request_id":"example-block-01"}' \
  'https://router.example/cgi-bin/proxy-guard-api/block'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "request_id": "example-block-01",
  "effective": true,
  "remaining": 120,
  "seconds": 120
}
```

<a id="api-cancel"></a>

### Отменить временную блокировку

`POST /cancel` принимает ID запроса. Принадлежность запроса определяется по UUID, прошедшему проверку, и ID. Устройства и программы с одним UUID считаются одним владельцем. Для корректного ID API может вернуть `cancelled: true`, даже если запрос уже истёк или отсутствует. `effective` и `remaining` описывают оставшуюся блокировку API. Расписание и сбой проверки могут продолжать блокировать трафик.

```sh
curl -H 'Authorization: Bearer YOUR_UUID' \
  -H 'Content-Type: application/json' \
  --data '{"request_id":"example-block-01"}' \
  'https://router.example/cgi-bin/proxy-guard-api/cancel'
```

HTTP 200

```json
{
  "ok": true,
  "uuid": "YOUR_UUID",
  "request_id": "example-block-01",
  "cancelled": true,
  "effective": false,
  "remaining": 0
}
```

### Распространённые ошибки

| HTTP-статус и ошибка | Что проверить |
| --- | --- |
| 401 `authentication_required` | UUID отсутствует или недействителен. Проверьте текущее значение в LuCI. |
| 403 `https_required`, `api_disabled` или `lan_required` | Проверьте HTTPS, состояние API или маршрут через зону `lan`. |
| 409 `configuration_pending`, `configuration_changed`, `protection_not_active` или `request_conflict` | Подтвердите настройки перед повтором диагностики либо проверьте режим защиты и длительность для уже действующего ID. |
| 429 | Действует интервал между диагностическими запросами или достигнут лимит блокировок. Учитывайте `Retry-After`, если заголовок присутствует. |
| 502 / 504 | Проверка не прошла или истёк её тайм-аут. Подробности могут быть в поле `diagnostics`. |
| 503 `busy` | Выполняется другая операция. Перед повтором подождите число секунд из `Retry-After`. |
| 503 `policy_not_ready`, `request_state_unavailable` или `firewall_failed` | Политика межсетевого экрана не готова, состояние запросов недоступно либо обновление правил завершилось ошибкой. Проверьте состояние защиты и журнал перед повтором с тем же ID запроса. |
