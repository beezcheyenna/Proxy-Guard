# Исходники, сборка и проверки

[English](BUILDING.en.md) · [简体中文](BUILDING.md) · [日本語](BUILDING.ja.md) · [Русский](BUILDING.ru.md) · [فارسی](BUILDING.fa.md)

В рецептах указаны Standard `0.3.0-21` и Pro `0.3.1-5`. Здесь описаны дерево исходников, сборка IPK и APK и тесты для разработчиков. Проверяйте каждый комплект по SHA256, полученным при его сборке.

## Дерево исходников

| Путь | Содержимое |
| --- | --- |
| `package/root/` | Файлы пакета Standard |
| `package/pro/root/` | Файлы пакета Pro |
| `package/Makefile` | Метаданные пакетов OpenWrt и обработчики установки и удаления |
| `package/i18n/` | Исходные строки, каталоги PO и метаданные генерации для пяти языков |
| `companion/vps/` | Linux Agent, пример конфигурации и установщик с ограниченной областью действий |
| `companion/worker/` | Шаблон Worker, файл фиксации зависимостей и тесты |
| `tests/` | Модульные, интерфейсные, системные и сетевые тесты, в том числе для выделенной среды |
| `LICENSES/` | Тексты лицензий и копии уведомлений исходных проектов |

Standard и Pro можно собирать по отдельности. Linux Agent и Worker находятся в `companion/`.

## Раздельная сборка IPK

В рабочей копии на Linux нужен Python 3. Переводы уже сгенерированы. Если исходные строки не менялись, загрузка LuCI и запуск инструментов перевода не требуются. Выберите одну из команд: для Standard, Pro или обоих пакетов соответственно.

```sh
python3 -B tools/build_ipk.py --only standard
python3 -B tools/build_ipk.py --only pro
python3 -B tools/build_ipk.py
```

При отдельной сборке Pro проверяется, что его файлы не пересекаются с файлами базового пакета. Пакеты, `SHA256SUMS` и списки файлов сохраняются в `dist/`. Сборщик создаёт файлы без запуска обработчиков установки и без подключения к устройствам.

После правки исходных строк подготовьте `po2lmo` из соответствующего официального исходного дерева LuCI. Для обновления только каталогов и отдельных страниц Pro добавьте `--only pro`.

```sh
python3 -B tools/build_translations.py /path/to/po2lmo
```

При изменении LMO и диагностических соответствий обновляйте и метаданные генерации. Инструменты LuCI, SDK, кросс-компиляторы и прокси-ядра поставляются соответствующими проектами.

## OpenWrt SDK

Поместите каталог `package/` проекта в `package/` подходящего OpenWrt SDK и по штатной процедуре SDK выберите `luci-app-proxy-guard` или `luci-app-proxy-guard-pro`. Зависимости берите из источников для целевой системы. Метка архитектуры `all` обозначает пакет скриптов.

Для 25.12 собирайте APK в соответствующем официальном SDK. `tools/build_ipk.py` создаёт только IPK. Ревизии APK записываются как `0.3.0-r21` и `0.3.1-r5`. Рецепт сохраняет обработчики установки, обновления и удаления APK и указывает минимальную версию Standard для Pro в нужном формате.

Рецепт SDK и Python-сборщик используют одни и те же деревья установки и выбирают обработчики для своего менеджера пакетов. `tools/test_sdk_staging.py` сравнивает подготовленные файлы, права и обработчики обоих собранных пакетов в изолированной ВМ с тестовым маркером. Сам инструментарий проверяется отдельной полной сборкой SDK.

Лицензии и уведомления входят в деревья установки. Pro устанавливает их отдельно от Standard.

## Базовые тесты

В подготовленной выделенной ВМ Linux или OpenWrt выполните:

```sh
python3 -B tools/test_standard_pro.py
```

Потребуются Python 3, Node.js, make и другие зависимости. Некоторые проверки версий и подготовки SDK требуют маркера `/etc/pgvm-fixture` из выделенного тестового образа. Не создавайте этот маркер вручную на хосте разработки.

Нативные Lua/ucode, обработчики установки, реальные LuCI/UCI/RPC, браузер, сетевые пространства имён, TCP/UDP и холодный запуск требуют соответствующих образов OpenWrt и тестовой оснастки. У отдельных сценариев есть требования к рабочему каталогу. Диски ВМ и рабочие учётные данные в репозиторий не входят.

Для проверки LMO и реального LuCI gettext укажите через `PG_LUCI_CBI` файл `cbi.js` из соответствующих официальных исходников. Записывайте результаты симуляции и реальной интеграции отдельно.

## Worker

В отдельной рабочей копии на Linux установите инструменты из файла фиксации зависимостей. Для облачных проверок используйте контролируемые тестовые ресурсы.

```sh
cd companion/worker
npm ci
npm test
```

`npm test` проверяет локальную среду. Команды развёртывания, секреты и привязки описаны в [руководстве Worker](CLOUDFLARE-WORKER.ru.md). Перед развёртыванием проверьте привязки, учётные данные и соединения целевой учётной записи.

## Охват тестов

Проверялись логика, установка, интерфейс, восстановление, IPv4/IPv6, холодный запуск, совместимость с несколькими системами и интеграция Cloudflare. После изменений запустите соответствующие проверки. См. [совместимость](COMPATIBILITY.ru.md) и [матрицу тестирования](TEST-MATRIX.ru.md).
