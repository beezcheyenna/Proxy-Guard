<a id="guide-setup"></a>

## インストールと初期設定

1. LuCI のパッケージ画面から対応する通常版をインストールします。opkg のファームウェアには IPK、apk のファームウェアには APK を使用します。VPS 機能が必要な場合は、互換性のある Pro も追加します。
2. 「サービス → Proxy Guard / プロキシ接続保護」を開き、ウィザードで SOCKS、クライアント、入口、IPv4 / IPv6 の範囲と例外を確認します。まず「監視のみ」で有効化して保存・適用し、案内に従って確認したうえで結果を確認します。
3. 遮断保護を使う準備ができたら保護モードに切り替え、再度「保存して適用」を選びます。自己診断に合格したら **30 秒以内に確認**してください。自己診断の失敗や未確認時は以前の設定に戻ります。通常のプロキシ障害は遮断保護の手順で処理されます。

初期状態では、保護・出口 IPv4 の照合・スケジュール保護は無効です。編集は設定案を変更し、「保存」は一時保存、**「保存して適用」で送信**します。設定画面からウィザードの再実行、前回確認済み設定の読み込み、UCI の直接編集も行えます。

## システム要件と保護範囲

<a id="guide-requirements"></a>

### 対応するシステムとプロキシクライアントは？

ルーターには **opkg または apk + LuCI + firewall4/nftables** が必要です。Lua、ucode、curl などの依存パッケージは、ファームウェアに対応する配布元から入手できる必要があります。24 系には IPK、25.12 系には APK を使用します。具体的な組み合わせは[互換表](COMPATIBILITY.ja.md)を確認してください。

PassWall、PassWall2、OpenClash、Nikki、HomeProxy に対応するアダプターを備えています。対応状況はクライアントの版、コア、転送モードにより異なります。プロキシコアと転送モードごとに制限があります。[互換表](COMPATIBILITY.ja.md)を確認してください。IPK と APK は相互に利用できず、fw3/iptables のみのシステムには対応しません。`all` は全機種・全アーキテクチャの検証済みを意味しません。

Pro の Linux Agent には Python `3.10+`、nftables、必要なカーネル機能が必要です。systemd / OpenRC に対応します。Ubuntu、Debian、Rocky Linux、Alpine Linux の指定リリースで互換性テストを行っています。[Linux 導入手順](LINUX-AGENT-INSTALL.ja.md)をご覧ください。

<a id="guide-scope"></a>

### 保護できる通信と構成上の制限は？

- **本機を通過する通信だけが遮断対象です。** 同一サブネット内の NAT を使わない補助ルーターでは、戻り通信が本機を通らないことがあります。その通信は遮断できません。本機をスイッチとして通過し、別のゲートウェイを使う端末も保護経路の対象外です。
- 選択した端末やサブネットについて、本機を実際に通過する IPv4/IPv6・TCP/UDP の双方向通信と既存接続を保護対象にできます。ルーター自身が開始する通信は、これらの端末の保護範囲には含まれません。
- NAT、ネットワークインターフェース、システム経路、DNS、プロキシクライアント設定は変更しません。LAN・DNS・管理アクセスの維持には、正しい保護範囲と例外設定が必要です。
- フローオフロード、ブリッジフィルタリング、カーネル機能の不足によって保護を有効にできない場合があります。メーカー独自の高速化、物理ポート、複数入口、VPN、コンテナー経路は実機で確認してください。
- 1 回の成功は、全サイト・全 UDP アプリ・IPv6 出口の正常性を証明しません。サンプリング間隔、未対応ログ、新しい上流バージョンによる検出限界もあります。
- 保護を有効にする前に、実際の構成と通信経路を確認してください。まず 1 台で障害時の遮断、復旧、LAN、DNS、管理、別ゲートウェイの端末を確認してから範囲を広げてください。

### Pro に必要な構成と、個別更新の条件は？

Pro には互換性のある通常版と、別途導入する Linux VPS Agent が必要です。制御経路は直接 HTTPS または Cloudflare を選べます。拡張のインストールだけではクラウドリソースは作成されません。インターフェースに互換性があれば Pro だけを更新できます。通常版のセキュリティ、状態遷移、ファームウェア互換性、共通翻訳の修正には通常版の更新が必要になる場合があります。

<a id="advanced-settings"></a>

## 設定と運用

<a id="guide-options"></a>

### 主な設定の選び方

| 設定 | 設定時の要点 |
| --- | --- |
| 動作モード | 監視のみでは確認と記録を行い、遮断しません。保護モードで、障害やスケジュールに応じた通信制限を行います。 |
| ローカル SOCKS | プロキシクライアントが実際に提供するローカル SOCKS5 ポートを指定します。既定の `1070` は例であり、本プラグインはプロキシを作成しません。 |
| 入口デバイス | ルーティングを行う LAN ブリッジなど、保護対象の通信が入るレイヤー 3 デバイスを選びます。すべての物理ポートを無条件に選ばないでください。 |
| 保護対象アドレス | 実際の IPv4 端末またはサブネットを指定し、IPv6 は別に確認します。IPv4 端末を 1 台選んでも、その端末のすべての IPv6 アドレスが自動選択されるわけではありません。 |
| LAN の例外 | 別サブネットの必要なサービスも含め、到達性を維持する必要がある LAN だけを指定します。広すぎる例外は保護を弱めます。 |
| プロキシ入口と DNS ポート | 実際に使うポートを指定します。プロキシ入口の指定は明示的プロキシによる迂回を防ぐためのものです。DNS 例外は実際の宛先ポートに合わせ、両者を重複させないでください。 |
| 出口 IPv4 検証 | 既定では無効です。有効にする場合は信頼できる想定出口を指定し、新しく観測した任意のアドレスを自動的に信頼しないでください。 |
| サービス・ログ・起動時保護 | 新規インストールの保存済み設定では無効です。ただし、ウィザードは検出したクライアントに応じてサービス監視を推奨することがあります。概要と適用済み設定を確認してください。起動時保護には全体スイッチ、保護モード、サービス監視も必要です。 |
| 定時保護 | 既定では無効で、予定は未設定です。時刻、繰り返す曜日、固定 UTC オフセットを確認してから適用します。 |

HTTPS 検査先は 1 行に 1 件、`https://ホスト/パス|想定ステータスコード` の形式で指定します。例は `https://www.gstatic.com/generate_204|204` です。区切りの後の `204` は想定 HTTP ステータスコードで、URL の一部ではありません。2～4 件の検査先と、通常モードの 1 ラウンドで必要な成功数を設定します。既定の最小成功数は 1 件です。強化監視中は、すべての検査先で成功する必要があります。通信はローカル SOCKS を経由するため、検査先の障害やレート制限も結果に影響します。

新規インストール時の既定値は `https://www.gstatic.com/generate_204|204` と `https://connectivity-check.ubuntu.com/|204` です。上書きアップグレードでは、保存済みのカスタム検査先を引き継ぎます。

「接続チェック」で出口検証用の予備 HTTPS URL を指定できます。メインの URL がタイムアウトした場合に限り、同じ SOCKS 経路で予備の URL を 1 回試します。次回は再びメインから確認します。空欄の場合、ipify では https://4.ident.me/ を使用し、ほかのホストでは予備の問い合わせを行いません。どちらでも出口を検証できない場合は、既存の失敗判定が適用されます。

出口検証を有効にした場合、通常のアドレス確認には既定で ipify を使います。任意の Cloudflare 検査は、起動後にプロキシが初めて準備完了となった時と、各切断からの復旧時に 1 回ずつ追加で試みます。同じ切断の通知はまとめられ、毎日または継続的なポーリングは行いません。この機能も出口検証の有効化が条件です。Cloudflare trace を高頻度の検査先に追加しないでください。第三者の API は、永続的な提供やレート制限なしの利用が保証されるものではありません。

Cloudflare のタイムアウトや利用不能だけでは遮断しませんが、通常の検査には引き続き合格する必要があります。返された出口アドレスが期待値と異なる場合は、障害として扱います。

**初回確認の推奨順序：**

1. まず管理できる端末 1 台を選び、ゲートウェイ、IPv4 / IPv6 の経路、LAN・DNS・管理の例外を確認します。
2. 監視のみで有効にして保存・適用し、確認を求められたら確定します。サイトの検査結果、任意の出口検証、有効にしたクライアントサービスの検査を確認します。
3. 保護モードに切り替えて保存・適用します。自己診断に成功したら 30 秒以内に確定し、別の管理経路またはコンソールを確保します。
4. 管理可能な保守時間にプロキシの障害と復旧を再現します。利用する IPv4 / IPv6、TCP / UDP の新規・既存接続に加え、LAN、DNS、管理、別のゲートウェイを使う端末を確認します。
5. 確認後に範囲を広げ、定時保護や起動時保護を追加します。起動時保護を確認する際は、独立した管理経路を確保してから Proxy Guard が動作するルーターを再起動し、保護対象クライアントで起動中の遮断と復旧を確認してください。クライアントだけの再起動では確認できません。自己診断は実際の通信経路の検証に代わるものではありません。

更新前に、未確定の設定試用を確定または取り消してください。インストーラーは未確定の試用設定を先に戻し、確定済みの設定を保持します。UCI ファイルの直接編集にも適用と確認の手順が必要です。

<a id="guide-detection"></a>

### 接続チェック・遮断・復旧

#### 通常の接続確認

接続確認は設定したローカル SOCKS を必ず経由し、直接接続には切り替えません。出口 IPv4 の一致確認は初期状態では無効です。有効にする場合は、信頼できる期待アドレスを指定します。Pro は VPS からアドレス候補を取得できますが、ネットワークインターフェースやパネルのアドレスが実際のプロキシ出口とは限りません。確認後、保存して適用してください。

待受ポートの自動検出は、クライアントのサービス監視を有効にしている場合に使用できます。サービス監視を無効にする場合は、手動で設定した SOCKS ポートがクライアントの実際の待受ポートと一致していることを確認してください。SOCKS 認証は引き続き利用できます。

通常の接続確認では、既定で各ラウンドの終了後に 10 秒待機します。リクエストの所要時間は別途加算されます。連続 3 回の失敗で障害、連続 2 回の成功で復旧を確定し、これらの値は変更できます。画面が約 1 秒ごとに更新されても、通常の外部接続確認が毎秒行われるわけではありません。

固定の起動猶予は、既定ではルーターの起動から 150 秒後に終了し、保護モードではその間も通信を遮断します。起動時保護を有効にすると、この期限の代わりに必要なサービスの準備完了を待ち、その後、設定された遮断待機と復旧検査を行います。

#### サービスと実行ログの監視

クライアントのサービス監視を有効にすると、初期設定では監視対象の TCP・UDP・DNS のいずれかが停止・再起動した際に保護を開始します。実行ログ監視はサービス監視の下で別途有効にし、対応済みの上流メッセージを認識します。画面の言語を変えてもログの対応範囲は変わりません。UDP 経路確認を使うには SOCKS5 UDP ASSOCIATE 対応が必要です。

サービス監視は、現在のクライアント設定で必要なコンポーネントを対象にします。未設定または不要な UDP / DNS を一律に障害とはみなしません。クライアントを識別できない場合はアダプターと設定を確認し、検査対象外を正常確認済みと解釈しないでください。

#### 遮断と復旧

サービス監視で保護を開始した場合、初期設定では次の順序で復旧します。

1. **15 秒間、通信を遮断して待機**します。この間は外部への検証を行いません。
2. 待機が終わりサービスが準備できたら、新たにプロキシを検証します。復旧条件を満たした場合に通信を許可します。
3. 通信再開後に **60 秒間の強化監視**を行います。この間、正常であれば通信できます。新たな障害を検出した場合は、再度遮断して待機に入ります。

強化監視では、各ラウンドの終了から約 1 秒後に次の検査を開始します。リクエストの所要時間は別途加算されます。すべての HTTPS 検査先と、有効にした出口 IPv4・UDP 検査に合格する必要があります。いずれかが失敗すると、通常モードの最小成功数や連続失敗回数を使わず、再度遮断します。

待機、強化監視、それぞれの時間は設定できます。ログで検出した障害の最初の復旧では、その起動サイクルの新しい完了メッセージ、サービスの復旧、新たなプロキシ検証がそろった後に追加待機を省きます。スケジュール期間終了時も、サービス監視が有効で、別の障害や未完了の待機がない場合に限り同じ復旧フローを使います。強化監視中の新たな障害では、再び遮断して待機します。起動時保護は別途有効にしてください。[検出の動作](USAGE.ja.md)と[ログの互換性](LOG_COMPATIBILITY.ja.md)に詳細があります。

<a id="guide-schedule"></a>

### スケジュール・状態・言語

#### スケジュール

スケジュール保護は新規インストール時には無効で、**時刻や曜日は事前入力されません**。毎日の繰り返し、または毎週の任意の曜日を複数選べます。日付をまたぐ時間帯は開始日の予定として扱います。時刻は固定の UTC オフセットで、初期値は `UTC+00:00` です。夏時間には自動追従しません。 更新時は、保存済みの UTC オフセットとスケジュールを維持します。

たとえば月曜日だけを選び、開始を `22:00`、終了を `06:00` にすると、選択した UTC オフセットで月曜夜から火曜朝まで遮断します。火曜日を追加で選ぶ必要はありません。この例から予定が自動作成されることはありません。遮断するのは対象端末のインターネット通信で、LAN・DNS・管理には設定済みの例外を適用します。

#### 状態とログ

画面は状態、イベント、確認の詳細を自動更新します。プロセス監視と回数制限付きの自動復旧は、プラグイン自身の異常を対象とします。プロキシ障害は保護フローで処理します。プラグインのログはメモリー上にあり、再起動で消えます。別途設定されたシステムの永続ログは、この設定の対象外です。

#### 表示言語

画面は LuCI の言語設定に従い、**簡体字中国語・英語・日本語・ロシア語・ペルシャ語**に対応します。このページの上部で説明の言語を切り替えられます。

<a id="guide-troubleshooting"></a>

#### 状態表示の見方

現在の保護状態はカーネルの実際のルールを反映します。「前回の検査に合格」は過去の結果であり、現在の通信許可を保証するものではありません。通信許可が期限切れになると、遮断中または再検証待ちと表示します。

| 状態・表示 | 意味と次の確認 |
| --- | --- |
| 無効 | 本プラグインによる遮断保護はありません。全体スイッチと適用済み設定を確認します。 |
| 監視のみ | 通信を制限せず監視しています。ログに障害があっても遮断ポリシーは導入しません。 |
| 遮断中・定時保護中 | 原因、現在の予定、サービス状態を確認します。警告は障害に正しく反応した結果の場合もあります。 |
| 遮断待機のカウントダウン | インターネット接続は遮断されたままで、外部検査はまだ行いません。待機後も復旧検査の成功が必要です。 |
| 接続復旧・強化監視中 | 正常な間は通信できます。新しい障害が発生すると再び遮断し、待機に入ります。 |
| LAN インターフェース待ち | 選択したデバイス名と実際の状態を確認します。本プラグインはインターフェースを作成・有効化しません。 |
| 状態が古い・取得不能・ルール未確認 | 現在の保護を確認できません。エラーを保存し、古い緑色表示に頼らず、プロセス、ルール、設定を確認します。 |

#### 更新・再インストール・問題の切り分け

更新前に本プラグインの設定を保存してください。Pro の認証情報、Agent の非公開設定、証明書も別途安全にバックアップします。更新では有効・無効や独自の待機時間などの設定を維持します。ただし、検査先が識別対象の旧プリセットと完全に一致する場合は、新しいプリセットへ移行します。インストール後に実際の検査先を確認してください。同じバージョンの修正版を入れる場合、opkg / apk がインストール済みと判断することがあります。配布元とチェックサムを確認し、[インストール参考](USAGE.ja.md#installation)の同一バージョン再インストール手順に従ってください。依存関係の検査は省略しないでください。Pro の単独更新には基本 API の互換性が必要で、新しい遠隔機能には Agent や Worker の更新が必要な場合があります。

メニューがない、ページが異常、RPC オブジェクトが見つからない場合は、インストール出力全体を保存してから LuCI に再ログインし、ページを更新します。通常はパッケージ内の処理がキャッシュ削除と RPC 再読み込みを行います。再ログイン後も異常が続く場合はインストール失敗や依存関係を調べ、ACL を広げたり、手動のサービス再読み込みをインストール成功の証拠にしたりしないでください。

自分のルーターで読み取り専用の確認を行う例：

```sh
if command -v opkg >/dev/null 2>&1; then
    opkg status luci-app-proxy-guard
else
    apk list --installed luci-app-proxy-guard
fi
/usr/libexec/proxy-guard status
/usr/libexec/proxy-guard logs
```

ログ消去は本プラグインのログだけが対象です。クライアントの元ログは消さず、通信も復旧させません。保護を解除する場合は全体スイッチを無効にして保存・適用します。プロセスの強制終了やアンインストールは、安全な一時解除手順ではありません。診断情報を共有する前に実アドレス、秘密情報、購読 URL、認証ヘッダーを削除し、脆弱性は下記の非公開メールで報告してください。

### Pro：VPS アクセス・SSH・リモート保守

Pro は認証した自宅のグローバル IP を同期し、選択した VPS サービスポートにポリシーを適用します。VPS サービスの正常性を通信再開の追加条件にできますが、ローカルのプロキシ検証にも合格する必要があります。 任意の帯域制限は、信頼できる計測データで確認したフォールバック接続だけが対象です。

#### ポートとポリシー

Pro が管理するのは、明示的に追加して有効にした VPS 本体のサービスポートだけです。待受ポートの検出は候補を示すだけです。未選択のポートは既存ファイアウォールに従い、Docker 転送や全ポートを自動管理しません。

各ルールで **許可リストのみ・標準の不正利用抑制・監視のみ**を選び、接続元、接続しきい値、時間を個別に設定できます。リモートポリシーには別の確認期間があり、**初期値は 60 秒**です。確認しなければ以前のポリシーに戻ります。パネル、API、サブスクリプションが選択したプロキシポートを共有する場合、同じ制限を受けることがあります。

動作モードと接続元の選択は別の設定です。「すべての接続元」でも標準モードのリソース制限は適用されます。旧設定の「制限なし」は、そのポートの保護を完全に迂回します。許可リストのみのモードでは、すべての接続元を指定できません。自宅 IP や静的許可リストが標準制限の対象外になるかは、ルールの接続元設定によります。

監視のみのモードでは、選択した業務ポートを遮断しません。別途有効にした SSH 管理には、その専用設定が引き続き適用されます。

#### 緊急 SSH アクセス

SSH は初期状態では管理対象外で、リモート保守も無効です。SSH 管理を有効にした場合、両方の認証済みハートビートが設定時間（初期値 60 秒）途絶えると、緊急アクセスを開始できます。新規設定の初期値では、自宅 IP の認可が戻るまでインターネット全体からの緊急アクセスを許可します。時間制限や管理用接続元への限定も選べます。継続公開は露出時間を延ばし、時間切れ後に利用できる接続元がなければ新規ログインできなくなる可能性があります。SSH 認証、システムファイアウォール、上流のセキュリティグループは引き続き適用されます。

#### 制御接続

制御経路には直接 HTTPS、または Cloudflare Worker・Tunnel/VPC を選べます。認証とポリシーの連携に使い、プロキシ通信そのものは中継しません。制御リクエストがプロキシを経由しないように設定し、直通経路を確認する必要があります。プラグインは経路や振り分け設定を変更しません。独立したプロキシ経路のハートビートは、ローカル SOCKS 経由で通信経路を確認します。制御の初期設定は IPv4 です。IPv6 通信の保護は、IPv6 のクラウド制御経路が検証済みであることを意味しません。[Pro 連携コンポーネントの設定](PRO-COMPANION.ja.md)をご覧ください。

独立したプロキシ経路には、専用のハートビート秘密情報と Agent の HTTPS 入口を設定します。直接 HTTPS では同じ Agent のベース URL を使えますが、制御は直通、経路確認は SOCKS 経由に分けます。Cloudflare モードの Worker URL は独立した入口には使えません。[接続設定の対応表](LINUX-AGENT-INSTALL.ja.md#control-and-path)を参照してください。

#### 固定のリモート保守

リモート保守は初期状態では無効です。VPS または対応する Xray コアの再起動を要求するには、ルーターと VPS Agent の両側で対象操作を認可する必要があります。要求の受理は復旧完了を意味しません。続く検証結果を確認してください。任意のリモートコマンド実行は提供しません。

#### Pro の初回導入手順

1. 通常版のローカル保護を確認してから、互換性のある Pro をインストールします。
2. 対象の Linux VPS に Agent を導入し、実際のサービス、ポート、依存関係、既存のファイアウォールを確認します。SSH またはコンソール経路を確保してください。
3. 直接 HTTPS または Cloudflare 制御を選び、必要な認証情報をそれぞれ設定します。制御通信がプロキシを迂回することを確認します。SSH 緊急アクセスを使う場合は、プロキシ経由の独立した HTTPS ハートビートも設定します。
4. まず認証、許可、サービスの状態を確認します。待受検出は候補の提示だけです。管理対象のポートだけを追加し、パネル、購読、SSH と入口を共有していないか確認します。
5. 保存・適用して VPS の試行ポリシー結果を確認し、遠隔側の期限内に確定します。既定は 60 秒です。通常版のローカル 30 秒確認とは別の処理です。
6. SSH 管理、追加の遠隔ヘルス条件、遠隔保守は必要なものだけを有効にし、個別に確認します。同期の停止だけでは VPS ルールは削除されません。削除には専用の準備・適用・確認手順を使います。
