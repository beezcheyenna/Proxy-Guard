# 互換性と制限

[English](COMPATIBILITY.en.md) · [简体中文](COMPATIBILITY.md) · [日本語](COMPATIBILITY.ja.md) · [Русский](COMPATIBILITY.ru.md) · [فارسی](COMPATIBILITY.fa.md)

ファームウェア・OS、カーネル、アーキテクチャ、クライアントの正確なバージョン、実施日、未検証項目は [テストマトリクス](TEST-MATRIX.ja.md) に記載しています。インストール、更新、LuCI/RPC、障害時の遮断、復旧、コールドスタートを確認しました。パッケージ名の `all` はスクリプトパッケージを示します。

## ルーターとクライアント

LuCI と firewall4/nftables が必要です。opkg では IPK、apk では対応 SDK で作成した APK を使います。依存パッケージやカーネルモジュールはファームウェアに対応したフィードから取得してください。カーネル番号や ABI 表記が一致していても、別ベンダーのモジュールやオフライン一式で標準モジュールを上書きしないでください。

| クライアント | 検証したモード・項目 | 条件 |
| --- | --- | --- |
| PassWall / Xray, sing-box | TCP REDIRECT + UDP TPROXY、TCP/UDP TPROXY | IPv6 のプロキシには上流の IPv6 TPROXY を有効化します。REDIRECT の IPv6 は保護対象のルーティング通信を検証しました。 |
| PassWall2 / Xray, sing-box | TPROXY | REDIRECT などは別途検証してください。 |
| OpenClash / Mihomo | REDIRECT + TPROXY、TUN | サービス監視を無効にしても SOCKS 認証は維持します。IPv6 UDP プロキシは上流で明示的に有効化します。TPROXY と TUN を検証済みです。無効時は直接ルーティングされる場合があります。 |
| Nikki / Mihomo | REDIRECT + TPROXY、TUN | 既定の SOCKS 認証を維持し、選んだモードで確認します。 |
| HomeProxy / sing-box | REDIRECT + TPROXY、system TUN | 公式 sing-box 1.14.4 で IPv4/IPv6 の TCP/UDP を再検証しました。旧 sing-tun パッチは使っていません。 |
| PassWall / Hysteria2, Shadowsocks-Rust, NaiveProxy | ネイティブリスナーの認識、対応経路の遮断と復旧 | Hysteria2、Shadowsocks-Rust、NaiveProxy の HTTPS と QUIC を確認しました。NaiveProxy に UDP 中継はなく、IPv6 は保護対象のルーティング経路です。Shadowsocks-Rust の既定の IPv4 リスナーで IPv6 プロキシの動作は確認できません。 |
| PassWall / sing-box ShadowTLS v3 → ShadowTLS | TCP プロキシ、遮断と復旧 | 有効なテスト用プライベート CA で TLS を検証しました。UDP は別の保護対象ルーティング経路です。 |
| ShadowTLS | ネイティブクライアントのプロセスとリスナー | 標準クライアントは実験用のプライベート CA を信頼しないため、エンドツーエンドは未検証です。 |

Proxy Guard を導入していない環境で、上流の Xray 26.11.9 の複数 SOCKS5 UDP アソシエーションが一時 UDP ポートを重複使用してタイムアウトする事象を再現しました。この組み合わせの安定した UDP 中継は未確認です。UDP 検査を維持して原因を調べます。ほかの Xray トランスポートは別途確認してください。

UI、インストール済みパッケージ、実行中のコアのバージョンを別々に確認します。プロキシコアの導入はクライアント側で行います。OpenWrt、ImmortalWrt、iStoreOS の 24 系と 25.12 系が検証対象です。IPK と APK は使い分けます。fw3/iptables のみの環境は対象外です。ほかのファームウェア、カーネル、CPU では実際の経路を確認してください。

新規と既存の IPv4/IPv6 TCP/UDP、強化監視中の再障害、DNS・管理・ルーター自身の通信維持を確認しました。

## LuCI の言語とテーマ

通常版と Pro のページは簡体字中国語、英語、日本語、ロシア語、ペルシャ語を備えています。iStoreOS 24 の Argon と PassWall2 26.11.3-r1 を併用したとき、PassWall2 の初期化で LuCI の「自動」が英語になる事象を確認しました。LuCI のシステム設定で明示的に言語を選びます。システムメニューやほかのプラグインは各自の翻訳を使います。

## VPS Agent

Ubuntu、Debian、Rocky Linux、Alpine Linux でインストール、設定の保持、認証 API、IPv4/IPv6 TCP/UDP、対応メンテナンスを検証しました。3x-ui と Xray のバージョンを別々に確認し、適切なアダプターを選びます。

Python 3.10 以降、nftables、動的セット、レート制限、connlimit と対応カーネルモジュールが必要です。導入前に `--check-kernel` で確認します。systemd と Alpine OpenRC に対応します。対象は選択したローカル INPUT ポートと、一部の確認済みフォールバックフローの OUTPUT 応答です。NAT、FORWARD、Docker の公開ポート、別の名前空間、上流のセキュリティグループは対象外です。

検出されたポートは候補です。管理するポートを明示し、SSH 管理とメンテナンスは個別に許可します。SNI/REALITY の設定だけでは認証は確認できません。フォールバックの正確な帯域制限には信頼できる新しい構造化データが必要です。

## 保護モードの前提条件

UCI でソフトウェア・ハードウェアオフロードが有効、nft flowtable が残存、`bridge-nf-call-iptables` または `bridge-nf-call-ip6tables` でスイッチングのみの通信が IP ファイアウォールに流入、または入口・カーネル・ブリッジ・ルールを検証できない場合は確認を止めます。設定は機器側で確認してください。

ベンダー独自の高速化やスイッチチップのバイパスは実機で確認します。NAT なしの検証では戻りも同じルーターを通りました。同一サブネットのゲートウェイには行きの通信しか届かない場合があります。スイッチ経由で別ゲートウェイを使う端末は影響を受けないことを確認してください。サブネット間 LAN、VPN、コンテナー、複数ブリッジ、IPv6 既定経路も実構成で確認します。

## 検査と自動復旧の制限

HTTPS、任意の IPv4 出口照合、サービス検査、任意の IPv4 DNS UDP 検査は別々の経路を確認します。成功は測定した経路についての結果です。出口 IPv4 照合は新規インストールで無効、更新では設定を保持します。

サービスは約 1 秒ごと、ログは設定した 1～10 秒ごとに差分を読み取ります。短時間の変化は見逃すことがあります。認識は確認済みメッセージ、タイムスタンプ、動作段階に基づきます。時計が無効ならログからの復旧確認はできません。スケジュールは固定 UTC オフセットを使います。[実行ログの互換性](LOG_COMPATIBILITY.ja.md) を参照してください。

procd は終了したプロセスを再起動します。ウォッチドッグはハートビート異常時に本プラグインを限られた回数だけ再起動します。通常のプロキシ障害は保護手順で処理します。長時間無効にした後は再有効化時に起動猶予があり、再試行上限に達すると保護を維持して点検を促します。自動復旧はファイルシステム、カーネル、スケジューラー、procd、ウォッチドッグに依存します。ログは RAM にあり、システムログの保存はファームウェアの設定に従います。

## 配備時に確認すること

実際の配備で物理 NIC、高速化、非対称経路、長時間運転、新しいクライアント版を確認します。家庭側の公開 IP が変わったら新しいリースと古いリースの満了を調べます。Cloudflare のバインディングと接続も確認します。1 台から監視モードで始め、LAN、DNS、管理、別ゲートウェイ、IPv4/IPv6、既存接続、復旧を確認します。起動時保護を試す前に管理経路かコンソールを確保してください。
